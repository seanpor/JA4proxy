## What was deleted from this file (and why)

The previous version of Phase 60 contained a strategy restatement, a Python
performance baseline (2,184 conn/s), a "what work is already done" inventory,
a list of seven remaining gaps, a product limitations section, and a
relationship table to the 79–86 enterprise phases.

All of that is now stale or duplicated:

- **Python perf numbers** — Python proxy is deprecated. Production is the Go
  binary (`bin/proxy`, see CLAUDE.md). Python numbers are no longer the
  product baseline. Go production-load benchmarks land in Phase 86.
- **"Work already done" inventory** — `manifest.yaml` is the source of truth
  for completion status. Maintaining a parallel inventory in this file
  guarantees the two diverge.
- **"Real remaining gaps" list** — replaced by the rewritten Phase 61, 62,
  63, 64 documents and by Phases 200–203 (the more recent strategic
  security review). Phase 101 holds the cross-phase deferred items.
- **Product limitations** — moved to `docs/PRODUCT_LIMITATIONS.md` (or, if
  that file does not yet exist when you read this, the limitations are
  documented inline in the relevant phase files: fingerprint evasion in
  Phase 0, fail-open in Phase 14d, write-abuse threat model in Phase 34,
  WAF positioning in `README.md`).
- **Enterprise phase relationship table** — each enterprise phase document
  (79–86) declares its own dependencies in its preamble. A central
  relationship table is redundant and goes stale silently.

## Phases 61–64 in one paragraph each

These four phases are the "make the Go proxy enterprise-deployable" cluster.
They add **no new proxy capabilities** — no new signals, no scoring changes,
no new bypass rules. They are quality, supply-chain, observability, and
deployment validation work. Each has been rewritten on 2026-04-09 to assume
Go is production and to remove overlap with the more recent Phase 200–203
strategic security work.

- **[Phase 61](PHASE_61.md) — CI Test Pipeline + Repo Hardening.** GitHub
  Actions workflows that run Python and Go test suites on every push, SHA-pin
  the existing `ja4proxy-policy.yml` workflow, add Dependabot, write a
  branch-protection bootstrap script. **Does not** cover image build /
  SBOM / cosign signing — those live in [Phase 202](PHASE_202.md).

- **[Phase 62](PHASE_62.md) — Go Fuzzing, Adversarial & Chaos Test Parity.**
  Closes the test-category gap where Python has fuzz / adversarial / chaos /
  property-based / FP-corpus tests and Go has none. Adds Go native fuzzers
  for the ClientHello and PROXY-protocol parsers, an FP-corpus regression
  test, a pipeline-level chaos test, property-based tests via `rapid`, and
  the pre-enterprise validation report generator.

- **[Phase 63](PHASE_63.md) — Service Level Objectives.** Defines four SLIs
  (availability, latency, Redis correctness, FP rate), recording rules,
  multi-window multi-burn-rate alerts, and four SLO runbooks. Go-only —
  the metric naming work is already done (all `internal/metrics/metrics.go`
  metrics use the `ja4proxy_*` prefix). Adds one new gauge,
  `ja4proxy_tls_cert_expiry_timestamp_seconds`, that Phase 64 also depends on.

- **[Phase 64](PHASE_64.md) — Deployment Validation & Disaster Recovery.**
  Smoke tests for Docker Compose / Helm-kind / Podman-Quadlet, MTTR baseline
  measurement script, five DR scenario runbooks, GameDay design, credential
  rotation runbook, TLS certificate rotation runbook, rolling upgrade
  runbook. References (does not duplicate) the existing
  `docs/runbooks/redis_operations.md`, `docs/runbooks/go_proxy_operations.md`,
  and `docs/runbooks/security_incident_response.md`.

## Execution order and independence

After the 2026-04-09 rewrite the four phases are deliberately designed to be
**independent** so a junior contributor can pick up any one of them in
isolation:

| Phase | File ownership | Depends on |
|---|---|---|
| 61 | `.github/workflows/ci.yml`, `.github/workflows/ja4proxy-policy.yml`, `.github/dependabot.yml`, `scripts/branch_protection.sh` | nothing |
| 62 | `cmd/proxy/*_test.go`, `internal/tls/parser_test.go`, `internal/tls/ja4_fp_corpus_test.go`, `internal/security/pipeline_chaos_test.go`, `internal/security/property_test.go`, `cmd/proxy/bench_test.go`, `scripts/generate_validation_report.py` | nothing |
| 63 | `monitoring/prometheus/slo_recording_rules.yml`, `monitoring/alertmanager/rules/slo_alerts.yml`, `internal/metrics/metrics.go` (one new gauge), `docs/runbooks/slo_*.md` | nothing |
| 64 | `scripts/smoke/*.sh`, `scripts/measure_mttr.sh`, `monitoring/alertmanager/rules/tls_alerts.yml`, `docs/runbooks/disaster_recovery.md` + 4 sibling runbooks, `Makefile` | the gauge added in Phase 63 |

The only cross-phase dependency is the `ja4proxy_tls_cert_expiry_timestamp_seconds`
gauge: Phase 63 emits it, Phase 64 alerts on it. If Phase 64 runs first, the
alert rule lands but fires immediately on missing data — resolve by landing
the gauge subtask out of Phase 63 first or by gating the alert with `absent()`.

## When Phase 60 should be edited

Almost never. Edit this file only when:

1. The list of "what replaces it" pointers above changes (a new source of
   truth supersedes one of the existing ones).
2. Phases 61–64 are restructured *again* and the one-paragraph summaries
   above need to be re-aligned.
3. Someone proposes a new strategic governance document and we need to
   decide whether it lives in this file or in its own phase.

Do **not** add new content here. New strategy work goes in a new phase file
or in the gap register at `PHASE_101.md`.
