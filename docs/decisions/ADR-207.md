# ADR-207 — Nightly benchmark regression detection: textfile collector, not remote_write or Pushgateway

- **Status:** Accepted (Phase 805)
- **Date:** 2026-07-30
- **Builds on:** the self-hosted Prometheus/Grafana/Alertmanager stack (`deploy/docker/docker-compose.monitoring.yml`)

## Context

`make bench-macro` (`ja4p test benchmark`) is real, working performance
tooling, but nothing runs it on a schedule — a PR that regresses hot-path
latency or throughput passes CI cleanly. Fixing this needs the nightly
result to reach the observability stack already in production. Two
constraints shape every option:

1. GitHub Actions jobs in this repo run exclusively on `ubuntu-latest`
   (checked across every workflow) — ephemeral, no self-hosted runner.
2. The self-hosted monitoring stack (Prometheus/Grafana/Alertmanager,
   operated over the SSH-tunnel pattern in `make ssh-tunnels`) has **no
   inbound network path** from GitHub's cloud runners. This is deliberate —
   `DMZ_READINESS.md` and this project's whole security posture are built
   around minimizing inbound exposure to the monitoring stack.

## Options considered

| Option | Verdict |
|---|---|
| **Prometheus `remote_write` opened to CI** | Rejected. `prometheus.yml` already has a commented-out `remote_write:` stanza. Enabling it means exposing an ingest endpoint to GitHub's dynamic IP ranges, with credentials in Actions secrets — new inbound attack surface purely to carry benchmark numbers. |
| **Pushgateway** | Rejected. Adds a whole new always-on service (its own CVE/patch surface) purely to bridge one ephemeral nightly job to a scrape-based system. |
| **node-exporter textfile collector (chosen)** | node-exporter is already deployed and already scraped. Its textfile collector reads `.prom` files from a directory — zero new inbound ports, zero new services. CI publishes outbound to a public GitHub Release asset; a puller *already on the monitoring host* pulls it on a timer (outbound HTTPS GET only). |

## Decision

CI publishes `ja4p test benchmark --output json` results, enriched with the
regression-gate baseline and provenance, to a rolling GitHub Release asset
(`nightly-benchmark-latest`, `gh release upload --clobber`). A host-side
script (`scripts/export_ci_benchmark_textfile.sh`), installed via a systemd
timer on the monitoring host, curls that asset hourly and writes a
Prometheus text-exposition file that node-exporter's textfile collector
(newly enabled: `--collector.textfile.directory=/textfile`) picks up on its
normal scrape cycle. Fail-open on both fetch and parse failure — the script
leaves the last-known-good textfile untouched rather than blanking out good
data; a separate `JA4ProxyNightlyBenchmarkStale` alert (not this script)
covers the resulting staleness.

The regression threshold is 20%, gated on `throughput_cps` and
`p95_latency_ms` against `docs/reports/nightly_benchmark_baseline.json` — a
manually-curated file, updated only on a deliberate, reviewed capacity
change, never automatically. `p99_latency_ms` is trended but not gated
until enough nightly runs accumulate real p99 history.

### Grounding correction — a wiring bug found while implementing this

While verifying the alerting side would actually fire, `promtool check
config` against the real Prometheus mount set (matching
`docker-compose.monitoring.yml` exactly) failed: `slo_recording_rules.yml`
was referenced in `prometheus.yml`'s `rule_files:` but never mounted into
the container, and none of the 10 files under
`deploy/monitoring/alertmanager/rules/` (proxy, redis, security, backup,
tap, ebpf_attack, management_ui, slo_alerts, ti_feed, tls_alerts) were
mounted or referenced anywhere — despite being promtool-syntax-validated
(`make lint-prom`) and structurally tested
(`tests/unit/test_alert_rules.py`) for multiple prior phases. Prometheus, as
configured before this phase, would not evaluate any of them — the whole
directory was dark. Both gaps are fixed as part of this phase (see
`docs/phases/PHASE_805.md`'s design-correction notes and the Phase-805
comments in `docker-compose.monitoring.yml`/`prometheus.yml`), since this
phase's own two new alerts needed to actually fire to meet its acceptance
criteria, and fixing the wiring made that whole existing rule set live for
the first time as a direct side effect.

## Consequences

- No new inbound network exposure on the monitoring host; the puller is
  purely outbound.
- The monitoring host gains one new host-level artifact outside the
  docker-compose-managed surface (the systemd timer + puller script) —
  documented in `docs/runbooks/nightly_benchmark_regression.md`'s
  installation section so it isn't a mystery to the next operator.
- `docs/reports/nightly_benchmark_baseline.json` is a manually-gated file by
  design: a regression cannot silently raise its own bar by editing the
  baseline in the same PR that causes the regression, since baseline
  updates require deliberate review as a separate, explained change.
- Every alert rule under `deploy/monitoring/alertmanager/rules/` — not just
  this phase's two new ones — is now actually evaluated by Prometheus for
  the first time. Operators should treat any of those alerts firing for the
  first time as new information, not a re-confirmation of something already
  monitored.
