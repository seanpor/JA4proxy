# ADR-024 — Threat-Intelligence Feed Client: Hand-rolled vs `stix2` + `taxii2-client`

Date: 2026-04-08
Status: Accepted
Phase: 85

## Context

Phase 85 introduces an inbound threat-intelligence consumer under
`src/analytics/ti_feeds/`. The consumer polls TAXII 2.1 servers, parses STIX
2.1 indicators, and turns them into JA4proxy rules via the Phase 79 Management
API. The question at Prerequisite Gate 2 (PHASE_85.md §3) is whether to depend
on the OASIS-maintained libraries or hand-roll with `aiohttp`.

Candidate stacks:

1. **`stix2==3.0.1` + `taxii2-client==2.3.0`**.
   Maintained by OASIS. `stix2` parses bundles into typed Python objects and
   validates against the 2.1 spec. `taxii2-client` wraps the TAXII 2.1 REST
   endpoints.

2. **Hand-rolled**.
   Use `aiohttp` for HTTP, a small regex for pattern extraction
   (`r"\[x-ja4-fingerprint:value\s*=\s*'([^']+)'\]"` and a similar IP regex),
   and plain `json.loads` for STIX bundles. STIX objects are treated as `dict`
   with known keys (`id`, `type`, `pattern`, `confidence`, `valid_from`,
   `valid_until`).

## Decision

**Hand-roll.** Zero new transitive dependencies other than `jsonpath-ng` for
the unrelated `rest_generic.py` client.

## Consequences

### Positive

- `taxii2-client==2.3.0` is a synchronous `requests`-based client. The Phase 85
  feed runner lives inside the Python analytics container event loop alongside
  `stream_consumer.py` and `drift_detector.py`, which are fully async.
  Wrapping a blocking client in `run_in_executor` buys nothing and adds a
  threadpool that the rest of the container does not need.
- `stix2` 3.x pulls `stix2-patterns`, `simplejson`, `pytz`, `requests`,
  `requests-cache`, and a few indirect transitive packages. For a consumer whose
  entire STIX responsibility is "match a single pattern regex and read six
  well-known fields", this is substantial surface area to sign off on through
  the Phase 61 SBOM cycle. Zero new deps is a smaller blast radius.
- The Phase 20 TAP TAXII *publisher* (`src/tap/export/taxii_server.py`) emits
  JSON bundles directly with `pattern_type: "stix"`. The Phase 85 consumer
  therefore only needs to round-trip with a format we already control, not a
  spec we do not. A hand-roll lets us keep the two sides in exact lockstep.
- JA4 and IPv4/IPv6 pattern extraction is a regex. Hand-rolling keeps the
  parser under 40 LoC and trivially testable.

### Negative

- We lose the OASIS-maintained spec compliance check. Malformed STIX bundles
  are rejected by log + metric rather than by a library exception with a
  human-readable message. Mitigation: the adversarial test
  `tests/adversarial/test_ti_feeds_malformed_stix.py` covers truncated JSON,
  invalid UUIDs, malformed JA4 strings.
- If the upstream STIX spec adds a field we start needing, we have to add
  parsing code manually. At the current design scope (indicator polling,
  differential cleanup, nothing else), this is a feature not a bug.

### Neutral

- `jsonpath-ng` **is** a new dependency despite PHASE_85.md §6.4 claiming
  otherwise. It is required by the generic REST connector and was never
  actually added in Phase 46. Scope of use: `rest_generic.py` only.

## Reversibility

If operational experience shows a hand-roll cannot keep up with vendor STIX
variations (unexpected SCO extension fields, non-standard pattern expressions),
the hand-roll can be replaced with `stix2` in an additive commit. The hand-
rolled regex in `stix_ja4.py` is isolated to one module and one unit-test file,
and the `FeedClient` ABC does not expose STIX types in its interface —
implementers return `FeedPollResult` with plain strings.
