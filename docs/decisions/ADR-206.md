# ADR-206 — Go Redis restore: selective, GDPR-aware safety model

- **Status:** Accepted (Phase 315b)
- **Date:** 2026-06-13
- **Builds on:** ADR-205 (the backup artifact this restore reads)

## Context

Restoring a Redis snapshot is the *dangerous half* of backup/restore. Two ways it
can hurt people, both violating JA4proxy's core asymmetry (blocking a real user is
the expensive error):

1. **Re-blocking.** A snapshot captures every ban, the dial and the block-lists as
   they were at backup time. A naïve "restore everything" silently re-blocks users
   an operator has since un-banned — a mass false-positive event by construction.
2. **Resurrecting erased data.** `scripts/gdpr_delete.py` is the Right-to-Erasure
   path; it deletes a subject's per-IP keys and logs the erasure to
   `management:gdpr_erasure_log`. A backup taken *before* an erasure, restored
   *after* it, brings the erased person's data back — a GDPR Article 17 breach.

## Decision

Both failures are **impossible by default**:

1. **Allow-state by default; block-state only with `--include-blocks`.** Block-state
   = `ban:*`, `ban_cidr:*`, `ip:blacklist`, `ja4:blacklist`, `config:dial`. A
   default restore can never re-block a user; bringing bans back is a conscious act.
2. **GDPR tombstone check, read pre-flush.** Before writing any per-IP key, the
   restore consults a tombstone set built from the live `management:gdpr_erasure_log`
   **merged** with an optional host-mounted `--tombstone-file`. The live log is read
   **before** any `--force` `FLUSHDB` (which would destroy it). An erased subject's
   keys are skipped and counted. Subject-IP extraction handles IPv4 and IPv6
   canonically and never truncates v6 (JA4 strings contain no `:`, so
   `beacon:{ip}:{ja4}` splits on the last `:`). On any ambiguity we **skip** —
   failing to restore a ban is cheap; resurrecting PII is a breach.
3. **Integrity before any write.** Decrypt + GCM-verify + unpack the whole artifact
   first; a tampered/truncated/wrong-key artifact fails closed having written nothing.
4. **Refuse to clobber.** A non-empty target needs `--force` (which `FLUSHDB`s
   first). `--dry-run` reports counts and writes nothing.
5. **Schema downgrade-block.** A backup whose `schema_version` exceeds this binary's
   is refused (a full forward-migrator registry is deferred until a v2 schema exists).
6. **TTLs re-applied** from the artifact (a ban with 200s left does not return with a
   fresh hour). **Lock** via the same `backup:operation_lock`. **Audited** to
   `management:policy_audit` + `backup:last_restore` / `backup:restored_from`.

### Grounding correction

The command is `ja4p restore` (cobra CLI), not `ja4pd restore` — same correction as
315a; `ja4pd` is the daemon. The restore reuses 315a's `DecryptPayload`, the
`snapshot` format, the lock, and the CLI's `resolvePassphrase`/`redisConfigFrom`.

### Deferred (operational conveniences, not safety)

Full schema-migrator registry, `--prefix-map` sandbox remapping, and a post-restore
smoke test. Config-divergence is a **non-blocking WARN** (restore is already a
deliberate manual op), not an abort-unless-force.

## Consequences

- A default restore is safe to run; the destructive capabilities are all opt-in and
  audited. The three `ja4proxy_restore_*` alerts (plus `…_skipped_total`) now fire.
- Tests prove: bans gated by default, erased subjects never resurrected (file + live
  log, real Redis), tamper/schema/non-empty all fail closed, dry-run side-effect-free.
