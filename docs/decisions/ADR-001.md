# ADR-001: Redis Streams for Analytics (not Kafka or RabbitMQ)

## Status

Accepted

## Context

Phase 12 requires a durable, replayable event bus to carry per-connection metadata from
proxy instances to the analytics node. The analytics node performs cross-instance
aggregation, campaign detection, slow-scan detection, and score drift alerting. The
design requires:

- Multiple proxy instances writing events concurrently.
- A single analytics consumer reading events in order, with at-least-once delivery.
- Replay capability after analytics node restart or downtime.
- Fire-and-forget writes from the hot path (writes must not add measurable latency).
- Approximate retention of ~100,000 events (covering minutes to tens of minutes of
  traffic at typical rates).

Three options were evaluated: Redis Streams, Apache Kafka, and RabbitMQ.

## Decision

Use Redis Streams (`XADD` / `XREADGROUP`) for the analytics event bus.

## Consequences

### Positive

- **No new infrastructure.** Redis is already a hard dependency of the proxy (Phase 0).
  Adding Kafka or RabbitMQ would introduce a second stateful service, doubling
  operational complexity.
- **Persistent and replayable.** Redis Streams retain events until they are explicitly
  trimmed. After analytics node restart, the consumer group resumes from its last
  delivered ID with no event loss (within the retention window).
- **Consumer group semantics.** `XREADGROUP` provides exactly the semantics needed:
  multiple consumers in a group, at-least-once delivery, explicit ACK, pending entry
  list (PEL) for unacked messages.
- **Fire-and-forget `XADD` has < 0.1ms overhead.** Measured at < 0.1ms per write on
  the hot path, well within the proxy's latency budget. The write is async
  (`create_task`) and never blocks the connection handler.
- **100k events fits comfortably in Redis memory.** At ~500 bytes per event,
  100,000 events = ~50MB. Redis is already allocated well above this.
- **Approximate trimming is safe.** `XADD MAXLEN ~ 100000` trims at node boundaries,
  meaning the actual count stays close to 100k without per-write overhead. Slightly
  more than 100k entries is acceptable.
- **Operational simplicity.** Consumer lag, pending messages, and stream health are
  inspectable with standard Redis commands (`XINFO GROUPS`, `XPENDING`). No additional
  monitoring tooling needed.

### Negative

- **Single Redis is a SPOF.** If Redis is unavailable, events cannot be written. The
  proxy handles this by logging to a local buffer and re-emitting when Redis recovers
  (within the connection handler's fail-open path). Analytics findings from the outage
  window are absent.
- **Retention is bounded.** Events older than the MAXLEN trim point are lost. Kafka
  supports indefinite retention to disk. For JA4proxy's use case (near-real-time
  analytics, not compliance archival), bounded retention is acceptable.
- **Not suitable for very high throughput.** At > ~50,000 events/second, Redis Streams
  can become a bottleneck. The Python proxy's ceiling (~350 conn/s) makes this
  irrelevant. The Go rewrite (Phase 15) may revisit this if throughput grows to
  10,000+ conn/s on a single instance.

## Alternatives Considered

### Apache Kafka

- Pros: Designed for high throughput, unlimited retention, strong ordering guarantees,
  extensive consumer ecosystem.
- Cons: Requires 512MB+ JVM per broker, ZooKeeper or KRaft quorum, separate monitoring
  (Kafka UI or Confluent Control Center), complex deployment for what amounts to a
  100k-event ring buffer. Adds a significant operational burden to a lightweight
  security proxy deployment.
- Rejected: Operational overhead far exceeds the requirements. Redis Streams provide
  equivalent semantics at zero additional infrastructure cost.

### RabbitMQ

- Pros: AMQP standard, good consumer group support, lightweight relative to Kafka.
- Cons: Does not provide replay semantics by default (messages are consumed and deleted).
  Replay would require durable queues with no-ack and custom routing, which replicates
  Redis Streams behaviour with added complexity. Also introduces a second stateful
  service.
- Rejected: Lacks native replay. Redis Streams provide superior semantics for this use
  case.

### Redis Pub/Sub

- Considered and rejected early: Pub/Sub is not persistent. If the analytics node is
  offline when a message is published, the message is lost. Streams were specifically
  designed to solve this limitation.
