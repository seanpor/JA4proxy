# ADR-023 — Cloud Backup Storage Strategy: Hybrid Local + Cloud

Date: 2026-04-06
Status: Accepted
Phase: 57

## Context

JA4proxy backup artifacts are written locally by `BackupWorker.create_backup()`.
Local storage is fast and reliable for recovery within the same host, but provides
no protection against host failure, disk loss, or DR scenarios requiring off-site
copies.

The Phase 57 review identified three options:

1. **Cloud-only**: Route all backup I/O through a cloud API.
2. **Synchronous upload**: Write local first, then block the scheduler tick while uploading.
3. **Hybrid async upload**: Write local first (unchanged behaviour), then upload as an
   optional async step after the local write succeeds.

## Decision

Adopt the **hybrid strategy**: local backup is the primary recovery path; cloud is the
durable, off-site copy. The scheduler calls `await storage_adapter.upload(path, manifest)`
after `create_backup()` returns. Cloud upload failure is non-fatal — it logs a WARNING
and increments a Prometheus counter but never prevents the local artifact from being written.

For I/O wrapping: `boto3` (synchronous AWS SDK) and `google-cloud-storage` (synchronous
GCP SDK) are both wrapped with `asyncio.to_thread()` in their respective adapters. This
avoids the session-management complexity of `aioboto3` / `aiobotocore` without blocking
the event loop.

## Alternatives Rejected

- **Cloud-only**: Adds network latency to the backup hot path; a cloud outage or
  network partition leaves the operator with no local recovery path.
- **Synchronous cloud upload**: Blocks the scheduler tick; a slow or unresponsive cloud
  API would delay the next backup window. Cloud errors could fail an otherwise
  successful local backup.
- **`aioboto3` instead of `boto3 + asyncio.to_thread()`**: The async wrapper adds
  session-management complexity (separate session per coroutine, lifecycle management)
  without measurable benefit for a once-per-schedule upload that is already off the hot
  path.
- **Single provider only**: The operator survey found both AWS and GCP in active use
  among target deployments; both adapters ship in Phase 57b/57c. The `StorageAdapter`
  ABC makes adding further providers trivial.

## Consequences

- Cloud upload failure never blocks or fails the local backup (fail-open).
- Prometheus counter `ja4proxy_backup_cloud_upload_total{provider, result}` surfaces
  upload failures for alerting.
- Credentials are sourced from environment variables only (`AWS_ACCESS_KEY_ID`,
  `AWS_SECRET_ACCESS_KEY`, `BACKUP_GCS_CREDENTIALS_PATH`). They are never read from
  `config/proxy.yml` to avoid accidental secret exposure in config dumps.
- `StorageAdapter` ABC (5 abstract methods: `upload`, `download`, `list_backups`,
  `delete`, `verify_checksum`) defines the contract. New providers implement these 5
  methods only.
- `LocalStorageAdapter` is a reference no-op implementation useful for testing and
  single-host deployments where cloud upload is not needed.
