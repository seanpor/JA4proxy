# ADR-020: AF_PACKET vs pcap/Scapy vs PF_RING/DPDK for TAP Mode Capture

**Status:** Accepted
**Date:** 2026-03-28
**Phase:** 20 (Passive TAP/SPAN Mode)

---

## Context

JA4proxy TAP mode requires passive packet capture from a network interface to
fingerprint traffic without participating in any TCP connections. We evaluated
three capture backends:

1. **AF_PACKET (Linux raw socket)** — kernel-provided interface; requires
   `CAP_NET_RAW`; zero external dependencies; available on any Linux system.

2. **libpcap / Scapy** — userspace library wrapping AF_PACKET with a BPF
   filtering interface; Scapy adds Python-friendly parsing but at a performance
   cost (each packet becomes a Python object).

3. **PF_RING / DPDK** — kernel-bypass frameworks designed for line-rate
   (10+ Gbps) capture; require specialised NICs or drivers; not available in
   standard cloud VM environments.

## Decision

Use **AF_PACKET** (via Python's `socket` module with `socket.AF_PACKET`,
`socket.SOCK_RAW`) directly, with a purpose-built parsing layer in
`src/tap/capture.py`.

The Python capture layer calls `sock.recv(65535)` in a tight loop (per-worker
shard) and passes raw bytes to `_parse_ethernet_frame()`. Scapy is not used
in the hot path.

## Rationale

| Criterion | AF_PACKET | libpcap/Scapy | PF_RING/DPDK |
|-----------|-----------|---------------|--------------|
| Performance | Good (500k+ pps) | Poor (Scapy overhead) | Excellent |
| Dependencies | None | `scapy` | kernel modules + NIC |
| Deployment complexity | Low | Low | Very high |
| Cloud VM support | Universal | Universal | Limited |
| CAP_NET_RAW required | Yes | Yes | No (DPDK) / Yes (PF_RING) |
| Python integration | Native | Native (Scapy) | Difficult |

PF_RING/DPDK performance is irrelevant at our scale. The bottleneck is Python
signal scoring (~20µs/conn), not packet capture. AF_PACKET with multiple
parallel worker processes can saturate a 1 Gbps link for TLS-heavy traffic.

Scapy was rejected because each packet parse allocates a Python object tree
(Ethernet → IP → TCP → Raw), causing heavy GC pressure that limits throughput
to ~50k pps on a single core.

## Consequences

- TAP sensor requires `CAP_NET_RAW`. The process drops this capability after
  the socket is opened (principle of least privilege).
- A seccomp profile (`config/seccomp_tap.json`) restricts syscalls post-drop.
- BPF filter applied to AF_PACKET socket at bind time to drop non-TCP traffic
  before it enters the Python worker, reducing userspace processing by ~40%.
- If PF_RING/DPDK becomes necessary in the future, the capture interface
  (`src/tap/capture.py`) is isolated enough to replace the backend without
  changing the reassembly or fingerprinting layers.

## Alternatives Considered

- **tcpdump pipe:** Rejected — spawning a subprocess adds latency and makes
  error handling difficult.
- **Go capture layer feeding Python via Unix socket:** Rejected for Phase 20 —
  adds complexity without measurable benefit at current traffic levels. Will
  reconsider if Phase 26 throughput targets require it.
