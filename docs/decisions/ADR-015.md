# ADR-015: Go Proxy Rewrite — Language Selection

**Date:** 2026-03-17
**Status:** Accepted
**Deciders:** Engineering Team

## Context

The Python proxy (`proxy.py`) is the primary ingress for all TLS connections. It has proven
the design correct through Phases 0–14, but is bounded by the GIL: under high load,
a single Python process saturates at ~1,000–2,000 conn/s. The proxy runs multiple workers
via forking but this adds memory overhead.

We needed to evaluate whether to rewrite in Go or Rust for Phase 15.

## Decision

Rewrite in **Go**.

## Rationale

| Factor | Go | Rust |
|--------|-----|------|
| Throughput gain vs Python | 10–50× (GIL removed) | 15–60× |
| Borrow checker complexity | None | Significant |
| Time to implement | ~2 weeks | ~4–6 weeks |
| GC pause at 1,000 conn/s | < 1ms p99 | N/A (no GC) |
| Ecosystem (TLS, Redis, Prom) | Excellent | Good but less mature |
| Team familiarity | High | Low |

The marginal throughput advantage of Rust does not justify the complexity cost at the
traffic volumes this proxy handles (target: 10,000 conn/s per core). Go's GC pauses
at these scales are negligible.

## Consequences

- Python analytics container (`analytics/`) remains Python — scipy/pandas ecosystem
  has no Go equivalent and is not on the hot path.
- The Python proxy is kept in place for rollback; HAProxy upstream switching enables
  zero-downtime cutover.
- Redis key schema is unchanged — Go and Python share one Redis instance.
- Config schema (`config/proxy.yml`) is unchanged.

## Alternatives Considered

- **Rust**: Higher raw performance, but borrow checker complexity and longer development
  time outweigh the benefits at our scale.
- **Keep Python + uvloop**: Tested. At 5,000 conn/s the GIL becomes a bottleneck even
  with async I/O due to TLS parsing.
