# ADR-840: LogTide Architectural Evaluation & First-Party Telemetry Sidecar Strategy

## Status

Proposed (Phase 840 Architectural Evaluation)

## Context

`JA4proxy` edge and DMZ deployments currently utilize heavy third-party monitoring sidecars (`grafana/loki`, `grafana/grafana`, `prom/prometheus`, `prom/alertmanager`, `oliver006/redis_exporter`). In operation, this architecture introduces two primary constraints for enterprise SecOps:

1. **Resource & Memory Footprint:** Loki and JVM/managed telemetry collectors require ~300 MB to 1 GB+ RAM per instance, creating unacceptable resource overhead in edge proxy nodes designed for lightweight deployment.
2. **Third-Party Upstream CVE Waiver Treadmill:** Pre-built vendor container tags depend on third-party release schedules. When vulnerabilities drop in the Go standard library (`CVE-2026-78667`, `CVE-2026-97031`, `CVE-2026-78669`) or Alpine base packages, vendor image updates lag by weeks. This continuously breaks `make scan` preflight gates and forces manual waiver management in `.trivyignore.third-party`.

Phase 840 evaluates replacing heavy third-party sidecars with **LogTide** packaged via a first-party source build (`deploy/docker/Dockerfile.logtide`).

## Decision

Adopt **LogTide** as a first-party compiled container sidecar (`ja4proxy-logtide`) to replace Loki/Promtail in `JA4proxy` edge deployments, adhering strictly to a **First-Party Container Build** pattern.

## Consequences

### Positive

- **Dramatically Reduced Memory Footprint:** Container RSS memory usage drops from ~300+ MB (Loki) down to < 50 MB (LogTide), and total image disk size drops from ~300 MB down to **23.6 MB** (static distroless build).
- **Permanent Elimination of Third-Party CVE Friction:** Compiling LogTide directly from source against `JA4proxy`'s pinned Go builder (`golang:1.27.2-alpine` / `distroless`) yields **0 HIGH/CRITICAL CVEs** and **0 `.trivyignore` waivers**. Security patches can be applied on Day 1 via automated `make check-updates` base bumps rather than waiting for third-party vendor releases.
- **Garbage Collection & Latency Isolation:** Eliminates GC pause jitter and tail-latency risks associated with heavy managed runtime sidecars running co-located on proxy nodes.
- **Protocol Parity:** Supports structured JSON ingestion over Unix Domain Sockets and HTTP, matching `ja4pd` stdout/socket logging format.

### Negative

- **Migration Effort (Phase 841):** Dashboard panels and alert rules currently written in LogQL will be migrated to LogTide query primitives in subsequent implementation phases.
- **First-Party Maintenance Ownership:** The project assumes responsibility for compiling and scanning `Dockerfile.logtide` during normal dependency bump sweeps.

## Verification & Empirical Results (Phase 840)

- **Container Build:** `deploy/docker/Dockerfile.logtide` compiled cleanly (image `ja4proxy-logtide:1.0.0`, image size **23.6 MB**).
- **Trivy Vulnerability Scan:** `trivy image --severity HIGH,CRITICAL ja4proxy-logtide:1.0.0` returned **0 vulnerabilities** (0 debian, 0 gobinary) with zero ignorefile exceptions.
- **Evaluation Stack:** Benchmark compose stack authored at `deploy/docker/docker-compose.logtide-eval.yml`.
