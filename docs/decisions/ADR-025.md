# ADR-025 — Backup Format Versioning: 9-Byte Header

Date: 2026-04-06
Status: Accepted
Phase: 57a

## Context

The original backup format (`format.py`, Phase 19) had no header: it was a raw
sequence of length-prefixed entries. Each entry encoded one Redis key and its
`DUMP`-serialized value:

    [4B big-endian uint32 key_length][key bytes][4B big-endian uint32 value_length][value bytes]

This format has three problems:
1. It is impossible to distinguish a full backup artifact from an incremental one
   without reading the manifest sidecar.
2. The encryption flag (added in Phase 40) is recorded only in the manifest — the
   artifact itself has no indicator, so automated tooling cannot detect format type
   without the sidecar present.
3. It provides no path for future format evolution.

## Decision

Prepend a **9-byte magic header** to all new artifacts produced by Phase 57+:

    [4 bytes: ASCII magic "JA4B"]
    [1 byte:  format version = 1]
    [4 bytes: big-endian uint32 flags bitmask]

### Flags bitmask

| Bit | Constant | Meaning |
|-----|----------|---------|
| 0x01 | `FLAG_FULL` | Artifact is a full backup |
| 0x02 | `FLAG_INCREMENTAL` | Artifact is an incremental backup (reserved) |
| 0x04 | `FLAG_ENCRYPTED` | Payload is AES-256-GCM encrypted |

`decode_entries()` detects the magic bytes and skips the 9-byte header before
iterating entries. Legacy artifacts (no magic) are read from offset 0 unchanged.

## Why 9 Bytes

- **4-byte magic**: avoids false-positive collision with the legacy format. A valid
  legacy file would need to start with a key whose length is `0x4A413442` (= 1.24 GB),
  which is impossible for a Redis key name. The risk of false-positive detection is
  therefore astronomically low.
- **1-byte version**: supports 255 future format revisions without changing the magic.
- **4-byte flags**: provides 32 independent capability bits with zero additional overhead.

## Incremental Support Deferred

`FLAG_INCREMENTAL = 0x02` is reserved in the bitmask but no incremental artifacts are
produced in Phase 57. The dirty-tracking prerequisite (Phase 57d) was cut after an
architecture review found insufficient evidence of a production backup-size problem that
would justify the implementation complexity. It is deferred to Phase 58.

The reserved flag bit costs nothing and means incremental artifacts produced in a future
phase will be forward-compatible with all Phase 57-era readers.

## Consequences

- The SHA-256 checksum written to the manifest covers the full artifact including the
  9-byte header (integrity protection extends to format metadata).
- All artifacts produced by Phase 57+ have `format_version: 1` and `format_flags` in
  their manifests.
- Pre-Phase-57 artifacts remain readable indefinitely; backward compatibility is
  guaranteed and tested by `test_backup_roundtrip.py`.
- The `is_legacy_format()` helper in `format.py` makes the detection decision in O(4)
  bytes — no seek, no stat, no manifest read required.
