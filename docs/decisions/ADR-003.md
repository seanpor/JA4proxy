# ADR-003: RDAP Block Expansion Off by Default

## Status

Accepted

## Context

Phase 11 implements RDAP enrichment, which looks up the organisation that owns an IP
address's netblock via the RIR (Regional Internet Registry) RDAP API. When an IP is
confirmed to belong to a known-bad organisation (e.g., a hosting provider with a
history of bot traffic or abuse), the proxy can optionally expand the block to cover
the entire announced /24 (IPv4) or /48 (IPv6) — banning all IPs in that block.

This block expansion feature is powerful: it can proactively block thousands of IPs
before they ever connect. It is also dangerous for the same reason.

## Decision

RDAP block expansion is disabled by default (`rdap_enrichment.block_expansion.enabled: false`).
A secops admin must explicitly enable it. Even when enabled, multiple guards constrain
its behaviour.

## Consequences

### Positive

- **Default is safe.** A fresh deployment never automatically bans CIDR blocks. The
  proxy must be consciously configured to use expansion. This aligns with the core
  asymmetry principle: false negatives (missed bots) are recoverable; false positives
  (legitimate users blocked) are not.
- **Admin intent is explicit.** The operator who enables expansion has read the
  documentation, understood the risk, and made a deliberate decision. There is no
  way to accidentally enable expansion via a config typo or misconfiguration cascade.
- **The known-bad org list is the first gate.** Expansion only triggers for organisations
  that appear in `config/known_bad_orgs.yml`. A new RDAP lookup result cannot trigger
  expansion for an unknown org — the org must be pre-approved by the secops team.
- **Guards prevent runaway expansion:**
  - Maximum expansion per hour: `max_per_hour` cap (configurable, default: 5).
  - Maximum prefix size: never expands beyond /24 IPv4 or /48 IPv6. A /16 block could
    affect an entire ISP's customer base — this is categorically disallowed.
  - Expansion only on ban action: a connection must score above the ban threshold before
    expansion is considered (RDAP enrichment alone cannot trigger expansion).
  - Browser ALPN traffic is never enqueued for RDAP enrichment (ALPN h2/h1 bypasses the
    full pipeline, so their netblocks cannot be expanded).
- **Policy audit trail.** Every CIDR ban created by block expansion is written to
  `management:policy_audit`, providing a full record of what was blocked, when, and why.

### Negative

- **Expansion must be manually enabled per deployment.** Operators who want the feature
  must read the documentation and make an explicit config change. Some operators may
  not discover the feature.
- **Known-bad org list requires maintenance.** The list is static YAML — it does not
  auto-update. Orgs that change behaviour (legitimate hosting provider pivots to
  abuse-friendly) remain in the list until manually removed.
- **False positives still possible when enabled.** A shared hosting provider may appear
  on the known-bad org list while also hosting legitimate small businesses. The /24
  limit reduces but does not eliminate this risk. Operators must review expansion events.

## Alternatives Considered

### Block expansion on by default

- Rejected immediately. The blast radius of a single incorrect RDAP lookup or incorrect
  org classification could ban thousands of legitimate IPs. At dial=100, this would
  cause real user impact before anyone noticed. The asymmetry principle (false positive
  cost >> false negative cost) rules this out.

### Block expansion triggered by score threshold only (no org gate)

- Considered: allow expansion whenever an IP scores above the ban threshold, regardless
  of RDAP org lookup.
- Rejected: This would allow the analytics and scoring system to trigger CIDR bans
  automatically based on traffic patterns. A sophisticated adversary could engineer
  traffic patterns to trigger expansion of a competitor's IP range. The org gate
  provides a human-reviewed allow-list of known-bad infrastructure providers.

### Expansion up to /16 or /20

- Rejected. A /16 contains 65,536 IP addresses. Even a low false-positive rate (e.g.,
  1%) would block 655 legitimate users per expansion event. The /24 (256 IPs) and /48
  (equivalent user density) limits are the maximum acceptable blast radius.

### Per-RIR expansion limits

- Partially implemented: token buckets per RIR rate-limit RDAP lookups. This indirectly
  rate-limits expansion. But the hourly expansion cap is a separate, explicit limit
  that applies regardless of RDAP lookup rate.
