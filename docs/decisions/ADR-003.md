# ADR-003: Asymmetric Decision-Cache TTLs — ALLOW Long, BLOCK Short

**Date:** 2026-03-27
**Status:** Accepted
**Phase:** 1
**Deciders:** Security Architect, Lead Developer
**Last Reviewed:** 2026-06-11

## Context

The proxy caches its per-connection allow/block decisions (in-process
`LocalCache`, backed by Redis for cross-instance sharing) so it does not re-run
the full signal pipeline on every connection from a recently-seen client.

A cache entry has a TTL. The question is: should ALLOW and BLOCK decisions use
the **same** TTL? The project's governing principle says no. The core asymmetry
(`CLAUDE.md`):

| Error | Example | Cost |
|-------|---------|------|
| False negative | A bad bot slips through during a cache window | **Low** (recoverable) |
| False positive | A real browser is blocked | **High** (not recoverable) |

A wrongly-cached BLOCK keeps punishing a legitimate user for the whole TTL; a
wrongly-cached ALLOW merely lets a bad actor through a little longer. The TTLs
must reflect that the two errors are not equally costly.

## Decision

**Cache ALLOW decisions with a long TTL; cache BLOCK decisions with a short
TTL.** The reference values (configurable):

- **ALLOW: ~30 minutes.** A client we have judged legitimate stays fast and
  unblocked without re-scoring.
- **BLOCK: ~30 seconds.** A blocked client is re-evaluated quickly, so a
  mistaken or stale block self-heals fast and a lifted ban takes effect almost
  immediately.

A companion rule follows from the same asymmetry: **when Redis says "block" but
the local cache says "allow", the local ALLOW wins.** If Redis is degraded or
serving stale/poisoned block state, real browsers keep working.

## Consequences

### Positive
- A mistaken BLOCK decays within ~30 s instead of pinning a real user out for
  half an hour — the failure mode that matters most is the cheapest to recover.
- Lifted bans / whitelist additions propagate fast (short BLOCK TTL + pub/sub
  removals), while ALLOW traffic stays cheap (long TTL, few re-scores).
- Local-wins-on-conflict keeps legitimate traffic flowing during a Redis outage
  (consistent with the fail-open principle).

### Negative
- A genuinely-bad client whose BLOCK has expired may be re-served for up to one
  ALLOW window if it then scores below threshold — an accepted false-negative
  cost, bounded and recoverable.
- Two TTLs to reason about rather than one; documented here and in the cache
  layer so the asymmetry isn't "tidied" into a single value by a later refactor.

## Alternatives Considered

- **Symmetric TTLs (one value for both).** Rejected: it forces a false choice —
  short enough to heal bad blocks means constant re-scoring of good traffic;
  long enough to keep good traffic cheap means real users stay blocked for the
  whole window. The asymmetry exists precisely to avoid that trade.
- **BLOCK cached *longer* than ALLOW** (to "make bans stick"). Rejected: it
  inverts the cost model — it optimises for the cheap error (false negative) at
  the expense of the expensive one (false positive).
- **Redis as the authority on conflict.** Rejected: a Redis problem would then
  be able to block legitimate browsers; local-wins keeps the failure open.

## Go Implementation Note (phase-515, 2026-07-02)

The Go port's in-process `DecisionCache` (`internal/security/cache.go`) had
silently diverged from this ADR on all three counts: it was keyed on the **JA4
fingerprint alone** (not the client), it applied **no TTL** at all, and it made
**no ALLOW/BLOCK distinction**. Because a JA4 is shared by every client running
the same TLS stack, an IP-derived block cached under a JA4 was served to every
other client sharing that fingerprint — a permanent (no-TTL) false positive that
blocks real browsers — while an allow warmed by one client let an attacker with
the same ClientHello bypass every per-IP control. Tracked as
**JA4PROXY-2026-0087**.

Phase-515 restored the ADR-003 behaviour: the cache key is the composite
`clientIP + "|" + JA4` (isolates by client *and* fingerprint), ALLOW uses the
long TTL and every other action the short TTL, and expiry is enforced on read.
The TTLs are configurable under `decision_cache:` in `config/proxy.yml`
(`allow_ttl_seconds` default 1800, `block_ttl_seconds` default 30) and are
hot-reloadable; zero/absent values fall back to the ADR-003 defaults so a
partial config can never disable expiry.
