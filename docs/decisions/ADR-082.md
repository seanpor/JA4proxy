# ADR-082: Shadow Mode Signal Storage Backend

**Status:** Accepted
**Date:** 2026-04-07
**Phase:** 82 (Policy-as-Code, Shadow Mode & Governance)

---

## Context

Shadow mode (Phase 82) stores per-connection signal snapshots so that the proxy can
later replay scoring decisions at a hypothetical dial setting. This answers the
question: "If I had set dial=80 last week, what would have been blocked?"

The required data retention is 90 days. Estimating the storage requirement:

- ~500 bytes per connection (timestamp, source IP, JA4, score, signals array)
- ~14 million connections per month for a typical single-site enterprise deployment
- ~7 GB/month uncompressed
- ~90-day retention window = ~21 GB uncompressed

Two storage backends were evaluated:

| | Option A: Redis (LZ4 compressed) | Option B: ClickHouse |
|---|---|---|
| **Additional infrastructure** | None (uses existing Redis) | New ClickHouse container or cluster |
| **Estimated size at 90 days** | ~63 GB uncompressed; ~17 GB/month after LZ4 compression; ~50 GB total compressed | Same data, columnar format — ~8–12 GB |
| **Query performance** | Adequate for ≤ 10M connections per simulation window | Better for > 10M; supports arbitrary SQL aggregations |
| **Operational complexity** | Low — no new service to operate, monitor, or back up | High — ClickHouse requires backup, replication, and dedicated monitoring |
| **Recommended for** | Single-site deployments, ≤ 50M connections/month | Multi-site or high-volume deployments |

---

## Decision

**Option A (Redis with LZ4 compression)** is the default implementation for
deployments of ≤ 50 million connections per month.

**Option B (ClickHouse)** is recommended for deployments exceeding 50 million
connections per month. Switching from Option A to Option B requires setting
`shadow_mode.backend: clickhouse` in `config/proxy.yml` and deploying the
ClickHouse service. The `analytics/signal_retention.py` module abstracts the
storage backend; the simulation API and all other components are unchanged.

---

## Rationale

Option A requires no new infrastructure. At ~7 GB/month uncompressed with an
approximately 40% compression ratio from LZ4, 90-day retention costs roughly
50 GB of Redis memory. This is within the capacity of a standard enterprise
Redis deployment dedicated to the proxy.

Option B offers better storage efficiency and SQL-native querying at scale, but
introduces an additional service that must be operated, monitored, and backed up.
The complexity is not justified for the majority of deployments.

The `analytics/signal_retention.py` module encapsulates the storage backend behind
a small interface (`write_snapshot`, `query_range`, `delete_expired`). Swapping
Option A for Option B is a module-level change with no impact on the simulation
runner or API.

---

## Consequences

- Connection signal snapshots are written to Redis under the key pattern
  `sim:conn:{hour_epoch}:{conn_id}` (Hash, 90-day TTL).
- Simulation job state is stored under `sim:job:{sim_id}` (Hash, 7-day TTL).
- The analytics node gains a new `analytics/signal_retention.py` module responsible
  for writing snapshots and sweeping expired records.
- Deployments exceeding 50 million connections per month must deploy ClickHouse and
  set `shadow_mode.backend: clickhouse` in config. The default configuration targets
  Option A.
- Redis memory capacity must be considered before enabling shadow mode. Operators
  should verify available Redis memory before enabling 90-day retention.
