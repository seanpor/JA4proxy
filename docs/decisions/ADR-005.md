# ADR-005: RDAP Block Expansion Off by Default

**Date:** 2026-03-27
**Status:** Accepted
**Phase:** 11
**Deciders:** Security Architect, Compliance Officer, Lead Developer
**Last Reviewed:** 2026-03-27

---

## Context

RDAP (Registration Data Access Protocol) enrichment provides organizational information about IP addresses, including whether they belong to known-bad organizations. When a malicious IP is detected, the system could automatically expand the block to cover:

- The entire /24 IPv4 subnet (255 addresses)
- The entire /48 IPv6 subnet (equivalent density)

This "block expansion" feature was proposed to automatically block entire ranges owned by bad actors, preventing IP rotation within the same allocation.

## Options Considered

### Option 1: Block Expansion On by Default

**Behavior:** When an IP is blocked, automatically expand to its /24 (IPv4) or /48 (IPv6)

**Pros:**
- Automatically blocks IP rotation within the same allocation
- Reduces manual work for operators
- More effective against botnets using contiguous ranges

**Cons:**
- **High false positive risk:** Shared hosting providers, cloud providers, and residential ISPs often have legitimate users on the same /24 as bad actors
- **Collateral damage:** Blocking an entire /24 could affect hundreds of innocent users
- **Compliance risk:** May violate proportionality principles in some jurisdictions
- **Operational surprise:** Operators may not realize the scope of blocking

### Option 2: Block Expansion Off by Default (Opt-in)

**Behavior:** Block expansion is disabled by default; operators must explicitly enable it

**Pros:**
- **Safety first:** No risk of accidental mass blocking
- **Explicit consent:** Operator consciously accepts the false positive risk
- **Compliance safe:** Proportional response by default
- **Audit trail:** Enablement is a conscious configuration change

**Cons:**
- Requires operator awareness and action to enable
- May miss blocking opportunities if operator doesn't enable
- Additional configuration complexity

### Option 3: Block Expansion with Safeguards

**Behavior:** Expansion on by default but with automatic safeguards:
- Check against known good ASNs (cloud providers, CDNs)
- Limit to specific organization types (hosting providers only)
- Require multiple detections before expansion

**Pros:**
- Balances automation with safety
- Reduces but doesn't eliminate false positive risk

**Cons:**
- Complex logic that may fail or be bypassed
- False sense of security
- Still risky for shared infrastructure

## Decision

We chose **Option 2: Block Expansion Off by Default (Opt-in)**.

Block expansion is a powerful but dangerous feature that must be explicitly enabled by operators who understand the risks and accept responsibility for potential false positives.

## Implementation

```yaml
# config/proxy.yml
rdap:
  enabled: true
  block_expansion:
    enabled: false  # DEFAULT: false (opt-in)
    ipv4_cidr: 24   # Maximum expansion for IPv4
    ipv6_cidr: 48   # Maximum expansion for IPv6
    hourly_cap: 1000 # Maximum IPs that can be added via expansion per hour
```

```python
# src/security/rdap_enricher.py
def expand_block_if_enabled(ip: str, config: dict) -> list[str]:
    if not config.get("rdap", {}).get("block_expansion", {}).get("enabled", False):
        return [ip]
    
    # Perform RDAP lookup to get CIDR range
    cidr = rdap_lookup.get_cidr_for_ip(ip)
    
    # Apply hard caps
    expanded_ips = expand_cidr_within_limits(cidr, config)
    
    # Apply hourly rate limit
    if would_exceed_hourly_cap(expanded_ips):
        logger.warning("Block expansion hourly cap reached")
        return [ip]
    
    return expanded_ips
```

## Consequences

### Positive

**Safety First:** Default configuration cannot cause mass blocking incidents

**Compliance Safe:** Proportional response aligns with data protection principles

**Explicit Responsibility:** Operator must consciously enable and configure limits

**Audit Trail:** Configuration change is visible in git history and requires approval

**Educational Opportunity:** Forces operators to learn about block expansion before using it

### Negative

**Missed Blocking Opportunities:** Some botnet ranges may not be fully blocked if operator doesn't enable

**Configuration Complexity:** Additional knobs for operators to understand

**False Sense of Security:** Operators may think expansion is happening when it's not

### Safeguards for When Enabled

When an operator enables block expansion, these protections apply:

1. **Hard CIDR Limits:**
   - IPv4: Maximum /24 expansion (255 addresses)
   - IPv6: Maximum /48 expansion (equivalent to IPv4 /24 in population density)

2. **Hourly Rate Limit:** Maximum 1,000 IPs can be added via expansion per hour to prevent runaway blocking

3. **ASN Whitelist:** Known-good ASNs (cloud providers, CDNs) are exempt from expansion

4. **Audit Logging:** All expansion events logged with before/after IP counts

5. **Metrics:** `ja4proxy_block_expansion_ips_added` counter tracks expansion activity

## Revisit if…

1. **Improved IP reputation data:** If a high-accuracy IP-to-organization mapping becomes available that can reliably distinguish shared hosting from dedicated bad actor ranges
2. **Jurisdictional requirements:** If specific jurisdictions mandate automatic range blocking for certain threat types
3. **Operator feedback:** If >80% of production deployments enable expansion and request it as default
4. **False positive rate data:** If telemetry shows <0.1% false positive rate when expansion is enabled with current safeguards
