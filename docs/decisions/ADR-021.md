# ADR-021: EDL Pull vs Push for External Firewall Integration

**Status:** Accepted
**Date:** 2026-03-28
**Phase:** 20 (Passive TAP/SPAN Mode)

---

## Context

TAP mode produces a live feed of high-confidence malicious IPs that need to
be propagated to external firewalls (Palo Alto Networks, F5 BIG-IP, upstream
BGP routers, generic webhook consumers).

Two integration patterns were evaluated:

1. **Pull (EDL)** — Firewall polls a JA4proxy HTTP endpoint on a schedule
   (e.g. every 60 seconds) and downloads the current blocklist as a plain-text
   IP list (External Dynamic List / MineMeld format).

2. **Push** — JA4proxy actively pushes block decisions to firewalls via their
   REST/XML APIs as soon as they are detected.

## Decision

Support **both pull (EDL) and push** as complementary mechanisms. Neither is
disabled by default — operators configure which backends are relevant to their
environment.

- `src/tap/export/edl_server.py` — aiohttp HTTP server serving `/edl/{list_name}`
- `src/tap/export/f5_client.py` — push to F5 BIG-IP iControl REST
- `src/tap/export/palo_alto_client.py` — push via Palo Alto XML API
- `src/tap/enforcement_bridge.py` — iptables/ipset + BGP + webhook push

## Rationale

| Criterion | Pull (EDL) | Push (REST/XML/BGP) |
|-----------|-----------|---------------------|
| Simplicity | High — firewall does the work | Medium — JA4proxy must know firewall API |
| Latency | Bounded by poll interval (≥60s) | Near-real-time (seconds) |
| Reliability | Firewall retries on failure | JA4proxy must handle API failures |
| Firewall compatibility | Very broad (any firewall with EDL support) | Vendor-specific |
| State consistency | Firewall always has the current snapshot | Incremental pushes; can drift on restart |

Pull (EDL) is chosen as the **primary integration pattern** because:
1. Supported by Palo Alto, Fortinet, Checkpoint, Cisco, and virtually all
   enterprise firewalls.
2. The firewall drives the refresh cadence — no push failures to retry.
3. Reconnecting TAP instances get correct state automatically (pull model is
   self-healing).

Push is provided as an **acceleration layer** for use cases where 60-second
latency is unacceptable (e.g. active DDoS mitigation). Push supplements pull
rather than replacing it.

## EDL Design Decisions

- **ETag-based 304 caching** — reduces bandwidth for unchanged lists.
- **X-API-Key authentication** — firewalls must present a pre-shared key.
- **Source IP allowlist** — firewalls can only pull from configured CIDRs.
- **`max_age_hours` filter** — prevents ancient bans polluting the list.
- **`min_score` filter** — allows operators to tune sensitivity per list.

## Consequences

- EDL server adds a listener port (`tap_export.edl.port`, default 9099).
  Must be firewalled to allow only the polling firewalls.
- Push clients are fire-and-forget — failures are logged and counted in
  Prometheus but do not affect the hot path.
- BGP push validates prefix lengths (IPv4 ≥ /24, IPv6 ≥ /48) to prevent
  inadvertent route hijacking.
