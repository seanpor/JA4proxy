# ADR-205 — Go Redis backup: logical DUMP/RESTORE + AES-256-GCM artifact

- **Status:** Accepted (Phase 315a)
- **Date:** 2026-06-13
- **Supersedes:** the archived Python `BackupWorker` approach (`5afeba26`)

## Context

The Go proxy is stateless; all durable security state lives in Redis (bans, the
dial, allow/block lists, audit logs, fingerprints). There was **no Go backup
implementation**, and `deploy/monitoring/alertmanager/rules/backup.rules.yml`
alerted on `ja4proxy_backup_*` metrics that nothing emitted. We need a safe,
encrypted, restorable snapshot of the right Redis keys, emitted with those
metrics, without adding hot-path latency or requiring filesystem access to the
(possibly remote) Redis host.

## Decision

1. **Logical per-key `DUMP` / `RESTORE`, not `BGSAVE`.** `DUMP` returns Redis's
   own binary serialisation for *any* type and `RESTORE` rebuilds it exactly, via
   the go-redis client we already use. `BGSAVE` would need filesystem access to
   the Redis box, breaking the "Redis may be remote" model. The trade-off — a
   `SCAN`-based snapshot is best-effort point-in-time, not transactional — is
   acceptable for security state and is documented.
2. **Per-key explicit TTL capture (`PTTL`).** `DUMP` carries only the value, so we
   store each key's remaining TTL alongside it; `RESTORE key ttl value` re-applies
   it. Without this, restored bans would come back permanent.
3. **Encrypt the artifact with AES-256-GCM**, key derived from a passphrase via
   PBKDF2-HMAC-SHA256 (100k iterations, random 16-byte salt), random 12-byte
   nonce per artifact. The snapshot contains audit logs, bans and (excluded by
   default) credential material — a plaintext file would be a breach. GCM's tag
   also makes a tampered/truncated artifact fail closed on decrypt. Salt and nonce
   live in a plaintext header (neither needs secrecy, only uniqueness); the header
   is authenticated as GCM additional data.
4. **Paced, pipelined `SCAN`/`PTTL`/`DUMP`** (default batch 100, 10ms between
   batches) so a large keyspace doesn't monopolise Redis's single thread.
5. **Atomic write** (temp file + `rename`, artifact `0600`, dir `0700`), with
   count/age retention pruning.
6. **A default exclude-list is the security boundary:** ephemeral/regenerable keys
   and all credential/session/MFA material (`mgmt:totp`, `mgmt:webauthn`,
   `mgmt:saml`, `mgmt:oidc`, sessions) are never exported — they must regenerate,
   not be restored.
7. **Driven as a CLI subcommand** (`ja4p backup`), invoked by a timer/cron — no
   always-on goroutine, no hot-path impact. Metrics are emitted both to the
   process registry and (optionally) as a node-exporter textfile so a short-lived
   CLI run is still scrapable.

### Grounding correction

The phase plan said `ja4pd backup`, but `ja4pd` is the long-running proxy daemon
with no subcommand dispatch; the cobra CLI is `ja4p`. The backup subcommands live
in `ja4p` (`ja4p backup`, `ja4p backup inspect`).

## Consequences

- Backups are restorable for every Redis type, TTLs included; restore itself is
  the sister phase (315b) and is deliberately separate (it is the dangerous half).
- The `ja4proxy_backup_*` alerts can now fire/clear. The alert series was renamed
  `…_last_success_timestamp` → `…_last_success_seconds` per OBSERVABILITY_STANDARDS.
- miniredis only supports `DUMP` for string keys, so the every-type + IPv6
  round-trip is a real-Redis integration test (`-tags integration`); unit tests
  cover scope/exclude/retention/crypto/metrics.
