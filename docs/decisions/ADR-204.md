# ADR-204: Go Blocklist Feed Downloader — No Leader Election

**Status:** Accepted
**Date:** 2026-06-11
**Phase:** 309 (WP-6 — observability reconciliation)

---

## Context

The Go production proxy ships a `BlocklistManager` that holds in-process CIDR
tries (Spamhaus DROP/EDROP and any configured custom feeds) and consults them on
the hot path. Until now it only ever **loaded feeds from a local file** — and
nothing in the Go build ever populated that file. The config block
(`blocklists.feeds[]`) declared `url:` and `refresh_interval_seconds:`, but those
fields were inert: the path comment literally read *"if already downloaded."*

The practical consequences:

1. Spamhaus hard-blocking was effectively dead in Go production unless an
   out-of-band process happened to drop a file at the right path.
2. Two alerts — `SpamhausDownloadFailed` and `SpamhausListStale` — referenced
   metrics (`ja4proxy_blocklist_download_errors_total`,
   `ja4proxy_blocklist_last_refresh_success_seconds`) that no code emitted, so
   they could never fire. A never-firing alert is worse than no alert: it reads
   as coverage that does not exist.

The Phase 8 Python prototype had a `FeedManager` that performed downloads with
**leader election** (one instance fetches; others read the shared result), but
that prototype was deleted after the Go port and never reimplemented in Go.

## Decision

Implement a `FeedDownloader` in Go that fetches each configured feed on its own
timer and atomically swaps the parsed trie into the live `BlocklistManager`.
**Deliberately do not implement leader election** — every proxy instance
downloads every feed independently.

Supporting design points:

- **Conditional requests.** Each fetch sends `If-None-Match` with the last
  `ETag`; a `304 Not Modified` is treated as a successful refresh (the data we
  serve is confirmed current) and costs no parse.
- **Fail safe.** Any transport error, non-2xx status, parse error, or a body
  that parses to **zero** entries increments
  `ja4proxy_blocklist_download_errors_total{feed}` and **keeps the last-good
  trie**. We never blank out an existing blocklist because one fetch failed.
- **Bounded body** (64 MiB) guards against a hostile/over-large origin.
- **Warm restart.** On success the raw body is persisted (temp-file + atomic
  rename) to a per-feed cache path, default
  `/var/lib/ja4proxy/blocklists/<name>.txt`, and reloaded at boot so blocking is
  live before the first download completes.
- **Lock-free swap.** Each feed's trie lives behind an `atomic.Pointer`, so the
  hot-path `Check()` reads it without locking and a swap is a single pointer
  store.
- **Interval clamp.** `refresh_interval_seconds` is clamped to a 60s minimum so a
  config typo cannot become a self-inflicted DoS on the feed origin.

## Why no leader election

- **Correctness without a coordinator.** With leader election, followers depend
  on a live leader (and a shared store) to ever receive feed data. If the leader
  dies, followers silently go stale. Independent fetching means every instance
  always has fresh data — which is the fail-open posture the project mandates.
- **Load is negligible.** Spamhaus permits hourly polling; our default is every
  12 hours and the feeds are well under 1 MiB. Even a few dozen instances
  fetching every 12 h is trivial traffic, and `ETag`/`304` makes the steady
  state nearly free.
- **Simplicity.** No distributed lock, no shared-state replication, no
  leader-failover edge cases — all of which are extra failure modes on a hot,
  security-critical path.

If feed volume or instance count ever makes independent fetching undesirable, a
Redis `SET NX EX` refresh lock can be layered on later without changing the
swap/serve mechanics. This ADR records that we consciously deferred it.

## Consequences

- The two previously-dead alerts now fire on real signals. `SpamhausListStale`'s
  threshold was raised from 2 h to ~25 h to sit above the 12 h refresh interval
  (the gauge legitimately ages up to one interval between refreshes).
- A new per-feed disk cache path is written under `/var/lib/ja4proxy/blocklists/`
  (or an operator-set `path:`); deployments should make that directory writable.
- Each instance makes its own outbound request to the feed origin on the refresh
  timer. Egress allow-lists must permit it.

## Alternatives considered

1. **Leader election (Python-prototype parity).** Rejected for the
   availability and complexity reasons above.
2. **Delete the two alerts.** Rejected — feed download/staleness is a real
   operational concern; the right fix is to build the missing subsystem, not to
   stop watching for its failure.
3. **External cron/sidecar populates the file.** Rejected as the default — it
   pushes a load-bearing responsibility outside the proxy with no telemetry and
   no fail-safe; an operator may still do this by setting `path:` and leaving
   `url:` empty.
