# ADR-019: Backup & Restore Framework — Phase 19

**Date:** 2026-03-21
**Status:** Accepted
**Deciders:** Engineering Team

## Context

JA4proxy relies on Redis for state storage including configuration, blocklists, enrichment data, and analytics. Without a backup and restore mechanism, operational resilience is limited:

- No recovery path from accidental data corruption
- No migration path between Redis instances
- No disaster recovery capability
- No audit trail for state changes

Phase 19 implements a production-safe backup and restore framework with comprehensive observability and security hardening.

## Decision

Implement a **deterministic, non-destructive-by-default backup and restore system** with the following characteristics:

### Backup System
- **Deterministic key enumeration**: SCAN-based with stable ordering
- **Policy-based inclusion/exclusion**: Configurable key patterns
- **Never-backup guard**: Hard exclusion list for sensitive keys
- **Manifest validation**: Checksum verification and metadata
- **Retention management**: Age-based and count-based policies
- **Filesystem validation**: Security checks before writing backups

### Restore System
- **Non-destructive default**: Preserves existing keys not in backup
- **Explicit destructive path**: Requires `--force` flag for full wipe
- **Checksum verification**: Rejects tampered or corrupted backups
- **Audit logging**: All operations logged to `management:audit_log`

### Observability
- **Prometheus metrics**: Comprehensive backup/restore instrumentation
- **Structured logs**: JSON logs with subsystem tags
- **Alert rules**: Stale backup and failure rate alerts

## Rationale

### Why This Approach

| Factor | Decision | Rationale |
|--------|----------|-----------|
| **Backup scope** | Security-critical + operational keys only | Transient per-connection keys excluded to reduce size and complexity |
| **Encryption** | Not implemented in Phase 19 | Plaintext archives with filesystem hardening; encryption deferred to future phase |
| **Restore default** | Non-destructive | Safe default prevents accidental data loss |
| **Destructive restore** | Explicit opt-in only | Requires conscious decision with `--force` flag |
| **Key enumeration** | SCAN-based | Deterministic ordering, handles large key spaces |
| **Retention** | Dual policy (age + count) | Flexible retention management |

### Security Considerations

- **Never-backup patterns**: Hardcoded exclusion of sensitive keys (API tokens, passwords)
- **Filesystem validation**: Prevents writing to insecure directories
- **Audit logging**: Complete trail of all backup/restore operations
- **Checksum verification**: Detects tampering and corruption

### Observability Requirements

- **Metrics**: All backup/restore operations instrumented with Prometheus
- **Logs**: Structured JSON logs for all significant events
- **Alerts**: Proactive monitoring for backup failures and stale backups

## Consequences

### Positive
- **Operational resilience**: Recovery path from data loss scenarios
- **Migration capability**: Move between Redis instances safely
- **Audit trail**: Complete history of state changes
- **Disaster recovery**: Backup artifacts can be stored off-host
- **Compliance**: Meets basic data protection requirements

### Negative
- **Storage overhead**: Backup files consume disk space
- **Performance impact**: Backup operations add load to Redis
- **Complexity**: Additional operational surface area
- **No encryption**: Backup files are plaintext (accepted risk for Phase 19)

### Trade-offs
- **Plaintext backups**: Simpler implementation, but requires secure filesystem
- **Non-destructive default**: Safer, but may leave orphaned keys
- **Policy-based inclusion**: Flexible, but requires careful pattern management

## Alternatives Considered

### Alternative 1: Full Redis RDB Snapshots
**Rejected** because:
- Too coarse-grained (includes all keys)
- No policy-based exclusion
- No manifest validation
- Harder to implement incremental backups

### Alternative 2: Encrypted Backups
**Deferred** to future phase because:
- Adds significant complexity
- Key management challenges
- Performance overhead
- Phase 19 focuses on core functionality first

### Alternative 3: Cloud Storage Integration
**Deferred** to future phase because:
- Adds external dependency
- Complex credential management
- Phase 19 focuses on local filesystem first
