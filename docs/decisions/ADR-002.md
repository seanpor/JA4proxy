# ADR-002: Go for Phase 15 Rewrite (not Rust)

## Status

Accepted

## Context

The Python proxy has a hard performance ceiling of approximately 350 connections/second
per instance, caused by the CPython GIL serialising async I/O callbacks and TLS parsing
into a single thread. At this ceiling, each proxy instance adds ~5.7ms to allowed
connections and ~1.4ms to blocked connections, with Redis calls consuming ~0.5ms of
each event loop iteration.

Phase 15 is a full rewrite of `proxy.py` and `src/security/` in a compiled language to
remove the GIL and enable true multi-core TLS parsing. The target is 10–50× throughput
improvement. The Python analytics node, management UI, and configuration system remain
in Python (scipy/pandas/aiohttp are irreplaceable in those components).

Two candidates were evaluated: Go and Rust.

## Decision

Rewrite the proxy core in Go.

## Consequences

### Positive

- **GIL removed.** Go goroutines are scheduled across all available cores by the Go
  runtime. TLS parsing, scoring, and Redis calls run concurrently with no global lock.
- **Goroutines are a natural fit for per-connection handling.** The proxy's model is
  one goroutine per connection (accept loop spawns `go handleConnection(conn)`). This
  maps directly to Go's goroutine model with minimal architectural change from the
  Python async design.
- **`crypto/tls` and `net/tls` are production-grade.** The Go standard library TLS
  implementation has been used in production at scale (Cloudflare, Fastly, Google).
  JA4 fingerprint extraction from `tls.ClientHelloInfo` is well-supported.
- **GC pauses are negligible at this scale.** At 10,000 conn/s with Go's concurrent
  GC, pause times are typically < 1ms. The proxy's latency budget (P99 < 10ms) is not
  affected.
- **Faster to write and maintain than Rust.** Go's syntax is close to Python in
  verbosity. Interfaces, goroutines, and channels map naturally to the existing Python
  abstractions (async tasks, queues, signal collectors). The Go rewrite can be done by
  the same team that wrote the Python version with a short learning curve.
- **Excellent Redis client ecosystem.** `go-redis/redis` is the standard client;
  supports connection pooling, pipelining, Lua EVALSHA, and all Redis data structures
  used by JA4proxy.
- **Python analytics/UI stays Python.** Go handles only the hot path (TCP accept → TLS
  parse → score → forward). The analytics node and management UI are not performance-
  critical and retain the scipy/pandas/FastAPI ecosystem.
- **Stable, proven design.** By implementing Phase 15 last, the Go rewrite has a fully
  specified and tested Python reference implementation to work from. The API surface is
  stable.

### Negative

- **Two runtimes in the deployment.** Go proxy binary + Python analytics/UI. Docker
  Compose handles this transparently; no operator burden.
- **CGo required for MaxMind GeoIP.** The MaxMind Go library uses CGo for mmap
  performance. This adds a C toolchain dependency to the Go build. Alternative: use the
  pure-Go `oschwald/maxminddb-golang` library (slightly slower but no CGo dependency).
- **Bloom filter library portability.** The Python `redis-py-bloom` integration needs
  a Go equivalent (`RedisBloom` client). The `go-redis/redis` ecosystem has `RedisBloom`
  support via `redis-go-bloom`.

## Alternatives Considered

### Rust

- Pros: Zero-cost abstractions, no GC, best theoretical throughput, `tokio` async
  runtime is excellent, `rustls` is a high-quality TLS implementation.
- Cons:
  - **Borrow checker adds significant development time.** For a proxy that primarily
    does read-heavy pattern matching and pass-through forwarding, Rust's ownership model
    provides marginal safety benefit over Go's simpler memory model. The development
    time cost is 2–4× Go for equivalent functionality.
  - **GC pauses are not the bottleneck.** At JA4proxy's scale, Go's GC pauses are
    negligible. The theoretical throughput advantage of no-GC Rust is not meaningful
    until sustained > 100,000 conn/s, which is beyond the current target.
  - **Async Rust is more complex than Go.** `async fn` + `Pin<Box<dyn Future>>` +
    `tokio::select!` is significantly more complex to read and maintain than Go
    goroutines and channels.
  - **Smaller team knowledge base.** The team has Python and Go experience; Rust would
    require significant upskilling.
- Rejected: Marginal performance gain at this scale does not justify the development
  time cost and long-term maintenance complexity increase.

### C / C++

- Rejected immediately: Memory safety requirements, development velocity, and lack of
  a modern async I/O ecosystem make this unsuitable.

### Rewrite in Python with PyPy

- Tried conceptually: PyPy's JIT does not help with asyncio-heavy code in the same
  way it helps with CPU-bound loops. The GIL remains. The gain would be < 2× and
  would require compatibility work for aioredis and other extensions.
- Rejected: Does not solve the fundamental GIL constraint.
