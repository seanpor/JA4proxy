## A. Regulatory & legal posture

- [ ] **A1. What is your EU Cyber Resilience Act posture?**

- [ ] **A2. Provide your CRA Annex I evidence mapping (essential cybersecurity requirements).**
  Answer: [`CRA_CONFORMANCE.md` — Annex I](CRA_CONFORMANCE.md#annex-i--essential-cybersecurity-requirements). One row per ER1-ER13 with current-evidence file paths, gap, remediation.
- [ ] **A3. Provide your CRA Annex II evidence (vulnerability handling / SBOM / patches / support period).**
  Answer: [`CRA_CONFORMANCE.md` — Annex II](CRA_CONFORMANCE.md#annex-ii--vulnerability-handling-and-post-market-obligations). Note: the project does not commit a fixed support-period number; the position is documented per-row.
- [ ] **A4. What is your GDPR posture?**
  Answer: see [`GDPR_COMPLIANCE.md`](GDPR_COMPLIANCE.md) — the project ships features that **support** the operator's GDPR obligations (the operator remains the data controller). Privacy-framework alignment in [`iso29100-mapping.md`](iso29100-mapping.md).
- [ ] **A5. What PII does the product process and how long is it retained?**
  Answer: [`iso29100-mapping.md` — Data-flow](iso29100-mapping.md#data-flow) plus retention TTLs in [`../REDIS_SCHEMA.md`](../REDIS_SCHEMA.md). PII is limited to the source IP; retention bounded by per-key Redis TTLs.

## C. Supply chain

- [ ] **C1. Do you publish a Software Bill of Materials (SBOM)?**
  Answer: yes — CycloneDX SBOM attached to every container image, generated by [`.github/workflows/go-proxy-image.yml`](../../.github/workflows/go-proxy-image.yml) per [ADR-202d](../decisions/ADR-202d.md).
- [ ] **C2. Are container images signed?**
  Answer: yes — keyless `cosign` signing per ADR-202d.
- [ ] **C3. What SLSA level do you target?**
  Answer: currently SLSA Level 2 (signed + SBOM). Path to Level 3 documented in [ADR-107a](../decisions/ADR-107a-slsa-level-3.md). A `workflow_dispatch` verification workflow ([`slsa-verify.yml`](../../.github/workflows/slsa-verify.yml)) is already in place; L3 attestation wiring is in flight.
- [ ] **C4. Are GitHub Actions SHA-pinned?**
  Answer: yes — enforced by [`tests/test_workflow_pinning.py`](../../tests/test_workflow_pinning.py).
- [ ] **C5. Are your dependencies pinned and continuously scanned?**
  Answer: yes — see SSDF_MAPPING.md PW.4 and [findings.yaml](../security/findings.yaml) for CVE handling.

## D. Vulnerability handling

- [ ] **D1. What is your coordinated vulnerability disclosure (CVD) policy?**
  Answer: [`../security/CVD_POLICY.md`](../security/CVD_POLICY.md). Aligns with ISO/IEC 29147 + 30111. Safe-harbour text is the disclose.io Simple Safe Harbor template, verbatim.
- [ ] **D2. What is your CVD response SLA?**
  Answer: **no service-level commitment is made**, by design — see [`../security/CVD_POLICY.md` §3-4](../security/CVD_POLICY.md). The project responds on a best-effort basis. The "Why no SLA" rationale is recorded in the policy. Reporters who require a guaranteed response should arrange a commercial support agreement (none currently offered).
- [ ] **D3. Do you have a published security contact?**
  Answer: yes — GitHub Security Advisories, see [`../../SECURITY.md`](../../SECURITY.md) and CVD_POLICY §2.
- [ ] **D4. How are CVEs assigned?**
  Answer: via GitHub Security Advisories (GHSA-* → CVE), see CVD_POLICY §6.
