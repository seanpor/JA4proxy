- **Waiver expiry now means something, and fixing is cheaper than waiving (Phase 847d)**: the blind `exp:` re-dating is gone. `scripts/renew_trivyignore.py` no longer bumps a window — it re-affirms the premise of every expiring entry and takes one of four explicit actions: **DEAD** (no scan sees the CVE any more → the waiver is deleted and the derived ignorefiles re-rendered), **FIXABLE** (a newer upstream tag clears it → the fix is proposed, and the dates are left **untouched**), **UNMEASURED** (a declared carrier has no report, so the scan could not have seen it → escalated; a missing report is not evidence of absence), or **ESCALATE** (anything else → the exact next step is printed and the dates are left untouched). There is no longer any code path in the repo that extends an expiry: `renew_expiring()` and `render_waivers.py --renew` were deleted outright. Alongside it, the new `scripts/fix_forward.py` decides — with evidence — whether a clearing upstream version exists, and turns a `fixable` verdict into a reviewable `bot/fix-forward-*` bump branch carrying a before/after CVE table, or a `blocked` verdict into `fix_available: false` plus the concrete upstream change that would unblock it. The verdict is one of `fixable` / `blocked` / `unknown` with precedence blocked > unknown > fixable, and **`unknown` never claims either way**: an indeterminate constraint, a digest-pinned ref, an unreachable registry, or a failed candidate scan all yield `unknown` rather than a guess. The bot never creates a waiver and never merges. Two implementation findings are worth recording because both would have been silent: a CVE missing from the scan results is only *dead* if the scan actually covered the images the entry was pinned to (the renewal workflow writes no report for an image whose Trivy run fails, so an unguarded delete would have removed live waivers); and PyPI's metadata cap cannot be the 256 KiB used elsewhere — `aiohttp`'s metadata alone is 9.5 MB, and with the cap in place the whole `mcp`/`semgrep` constraint sweep was silently skipped and the verdict degraded from `blocked` to `unknown`, which only a **live** end-to-end run against real PyPI/OSV caught. The PyPI cap is now 32 MiB, justified by a measured high-water mark and reproducible via `--bytes-out`. The monitor (`make scan-monitor STATE_OUT=…`) now hands its findings to the bot, and an empty waiver registry is a valid end state rather than a schema error — zero waivers is the goal, not a mistake. See `docs/phases/complete/PHASE_847d.md`.
- **The `.trivyignore` renewal workflow had been measuring nothing for 63 days (Phase 847d)**: Phase 829a (2026-08-19) added `check_image_versions.py --list-third-party` to the re-affirmation workflow without installing PyYAML. `actions/setup-python` installs a **clean** interpreter, so the PyYAML the runner image happens to carry was not there, and the script exited 2 at import time. Every link in the chain was silent: the command substitution swallowed the exit code, so the image list came back **empty**; the Trivy loop scanned **nothing**; the drift check ran against an **empty directory**; `renew_trivyignore.py` died with `ModuleNotFoundError: No module named 'yaml'`; and `| tee` reported 0 regardless, because a pipeline's status is its last command's. **63 consecutive daily runs, all green.** The renewal safety net had been dead the whole time, and the "measured" report was measuring nothing — a check that measures nothing and reports success is worse than no check, because it looks like coverage while providing none. 847d's re-affirmation reads that same scan directory, so without this fix the feature would have been inert (every entry escalating, correctly, forever). Four guards now close the chain: PyYAML is installed on the runner in both workflows that need it; an empty image list is an explicit error and the step reports how many images it scanned; the script's own exit code is read via `PIPESTATUS` (the runner's `bash -e` otherwise aborts the step on the *expected* exit 1, and `| tee` reports 0 for any failure), so exit 1 means "a human needs to look" and exit 2+ fails the step loudly; and an ESCALATION — which changes nothing on disk — now files the tracking issue anyway, instead of being the one verdict that produced no artifact at all. `tests/unit/test_waiver_workflow_guards.py` asserts each guard, including that the dependency is real rather than spurious.
- **Four more defects found reviewing the 847d fix-forward work (Phase 847d)**: an adversarial read of the branch, plus the preflight gate, turned up four issues — three of them the exact failure this programme exists to remove, where something looks like "the exemption can go" and is not. (1) `load_registry()` coerced a **missing** `waivers:` key to `[]`, so a truncated edit or bad merge read as "zero waivers" and the derived ignorefiles would be regenerated **empty** — every live exemption dropped, silently; the key's absence is now refused at load time, while an empty list is still the valid goal state. (2) `_ENTRY_RE` matches prose inside a rationale's folded block scalar, so a rationale containing an indented `- id: parser` made `remove_entries()` delete only the target entry's *head* and leave its tail behind — the registry stopped being valid YAML; entry boundaries now honour the indent of the first entry. (3) `remove_entries()` could write a registry that did not parse; it now verifies before writing that the result parses and holds exactly the expected entries, failing closed with no partial write. (4) A Trivy report that analysed **nothing** (`"Results": null`, e.g. no detectable OS) still names the image, so it counted as coverage and a live waiver read as DEAD; coverage now requires `Results` to be a list, which is the shape `trivy_image_report.py` already treats as a genuine clean pass. The gate also caught SHA-1 in the scan-cache fingerprint — a content fingerprint, never a signature, but there is no reason to reach for a broken digest when SHA-256 costs the same. The generalisable lesson: every "is this exemption still needed?" check is only as good as its evidence, and "the file exists" is weaker evidence than it looks — a missing report, a report that analysed nothing, and a scan that never covered the image are three different things, and the first two are not evidence of absence. The same rule applies to the harness, not just to the evidence: "the job went green" is equally weak.
