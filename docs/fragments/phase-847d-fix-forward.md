- **Waiver expiry now means something, and fixing is cheaper than waiving (Phase 847d)**: the blind `exp:` re-dating is gone. `scripts/renew_trivyignore.py` no longer bumps a window — it re-affirms the premise of every expiring entry and takes one of four explicit actions: **DEAD** (no scan sees the CVE any more → the waiver is deleted and the derived ignorefiles re-rendered), **FIXABLE** (a newer upstream tag clears it → the fix is proposed, and the dates are left **untouched**), **UNMEASURED** (a declared carrier has no report, so the scan could not have seen it → escalated; a missing report is not evidence of absence), or **ESCALATE** (anything else → the exact next step is printed and the dates are left untouched). There is no longer any code path in the repo that extends an expiry: `renew_expiring()` and `render_waivers.py --renew` were deleted outright. Alongside it, the new `scripts/fix_forward.py` decides — with evidence — whether a clearing upstream version exists, and turns a `fixable` verdict into a reviewable `bot/fix-forward-*` bump branch carrying a before/after CVE table, or a `blocked` verdict into `fix_available: false` plus the concrete upstream change that would unblock it. The verdict is one of `fixable` / `blocked` / `unknown` with precedence blocked > unknown > fixable, and **`unknown` never claims either way**: an indeterminate constraint, a digest-pinned ref, an unreachable registry, or a failed candidate scan all yield `unknown` rather than a guess. The bot never creates a waiver and never merges. Two implementation findings are worth recording because both would have been silent: a CVE missing from the scan results is only *dead* if the scan actually covered the images the entry was pinned to (the renewal workflow writes no report for an image whose Trivy run fails, so an unguarded delete would have removed live waivers); and PyPI's metadata cap cannot be the 256 KiB used elsewhere — `aiohttp`'s metadata alone is 9.5 MB, and with the cap in place the whole `mcp`/`semgrep` constraint sweep was silently skipped and the verdict degraded from `blocked` to `unknown`, which only a **live** end-to-end run against real PyPI/OSV caught. The PyPI cap is now 32 MiB, justified by a measured high-water mark and reproducible via `--bytes-out`. The monitor (`make scan-monitor STATE_OUT=…`) now hands its findings to the bot, and an empty waiver registry is a valid end state rather than a schema error — zero waivers is the goal, not a mistake.
