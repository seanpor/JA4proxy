\section{The Problem: Bots Don't Look Like Bots Anymore}
\index{bots!modern evasion}\index{SSL inspection}\index{compliance}
% ─────────────────────────────────────────────────────────────────────────────

\newthought{A credential-stuffing campaign looks identical to human login traffic}
at the HTTP layer. The requests are syntactically valid. The user-agent strings are
plausible. The rate is low enough to evade simple counters. Your WAF's rule set
passes it. Your CDN's bot-score misses it because the attacker rotates IP addresses
faster than reputation feeds update.

The same is true of command-and-control frameworks. Sliver and Cobalt Strike ship
with configurable HTTP malleable profiles precisely to blend their traffic into the
noise floor of legitimate web requests. If your only detection surface is the
decrypted HTTP stream, you are already behind.

\sidenote{The Verizon DBIR consistently shows that credential abuse accounts for
more than 40\% of breaches. Most credential-stuffing toolkits ship with TLS stacks
that produce distinctive, stable fingerprints --- yet traditional defences never
inspect the handshake.}

Traditional TLS-aware defences --- SSL inspection, TLS termination proxies,
deep-packet inspection appliances --- do work, but they impose a substantial cost.
To inspect encrypted traffic, you must terminate TLS, decrypt, inspect, re-encrypt,
and forward. That requires holding your backend's private keys (or issuing your own
CA certificate that every client must trust). It introduces latency. And it creates
a significant compliance exposure: PCI-DSS, HIPAA, and GDPR all have strong opinions
about where and how key material is held and who can access decrypted traffic.
Regulated organisations frequently cannot deploy SSL inspection on their customer-
facing infrastructure without first satisfying legal and compliance review that can
take months.

\index{TLS!termination}\index{PCI-DSS}\index{HIPAA}\index{GDPR}

\begin{warningbox}[The compliance trap of SSL inspection]
  Every SSL inspection deployment requires answering: who holds the private key?
  Who can access the decrypted stream? What is the data residency of the plaintext?
  How is the inspection key rotated? These questions do not arise with \ja{}
  because \ja{} never decrypts anything.
\end{warningbox}

\newthought{The insight that changes this} is that you do not need to inspect the
encrypted payload to identify malicious clients. Bots, C2 frameworks, and scanners
reveal themselves in the one part of a TLS connection that is, by definition, always
transmitted in plaintext: the TLS~ClientHello.

\section{The JA4 Insight}
\index{JA4!fingerprint}\index{TLS!ClientHello}
% ─────────────────────────────────────────────────────────────────────────────

\newthought{Before a single byte of encrypted data is exchanged,} every TLS client
announces its capabilities. This announcement --- the ClientHello message --- is
transmitted in cleartext as the very first packet of a TLS session. It contains:

\begin{itemize}
  \item The list of cipher suites the client is willing to use, in preference order
  \item TLS extensions and their values (SNI, ALPN, session tickets, etc.)
  \item Supported elliptic curves and point formats
  \item The TLS version range the client supports
\end{itemize}

\sidenote{A TLS ClientHello is always plaintext --- this is not a protocol weakness
or a data leak. It is a necessary consequence of the negotiation: you cannot encrypt
a message to propose an encryption scheme.}

Because this information reflects the TLS stack of the client software, it is
remarkably stable. Sliver 1.5.x produces the same ClientHello whether it is running
from a datacenter in Frankfurt or a compromised laptop in Tokyo. Upgrading the \emph{payload}
has no effect on the fingerprint. The only way to change the fingerprint is to change
the TLS library or its configuration --- and that is a meaningful engineering cost
for an attacker maintaining a production C2 framework.

\index{Sliver C2}\index{Cobalt Strike}\index{Evilginx}

\subsection{JA4 vs.\ JA3}
\index{JA3}\index{JA4!improvements over JA3}

JA3 was the first widely-adopted TLS fingerprinting scheme (introduced by Salesforce
in 2017). It hashes the concatenated cipher suites, extensions, elliptic curves, and
elliptic curve point formats into a 32-character MD5 string. JA3 is still useful, but
it has well-documented limitations: it is order-sensitive, so different orderings of
the same capabilities produce different hashes, and benign TLS library updates
frequently caused false-positive fingerprint matches that required manual maintenance
of allowlists.

JA4 (introduced by FoxIO in 2023) addresses these problems:

\begin{itemize}
  \item Ciphers and extensions are \emph{sorted} before hashing, eliminating
        order-dependent variation
  \item The fingerprint is structured into three readable sub-components separated
        by underscores, making it possible to interpret a fingerprint without a lookup
        table
  \item ALPN is captured as a first-class field, allowing precise distinction between
        browser traffic (which advertises \code{h2}/\code{h1}) and non-browser traffic
  \item GREASE values are excluded, preventing false divergence between conformant
        implementations
\end{itemize}

\sidenote{\textbf{JA4 structure:} \code{t13d1516h2} encodes: \code{t}~=~TLS,
\code{13}~=~TLS~1.3, \code{d}~=~SNI present, \code{15}~=~15~ciphers,
\code{16}~=~16~extensions, \code{h2}~=~ALPN is h2.}

\section{How \ja{} Works}
\index{pipeline}\index{fast path}\index{signal collection}
% ─────────────────────────────────────────────────────────────────────────────

\newthought{\ja{} places itself between your load balancer and your backend} as a
TCP passthrough proxy. It never terminates TLS. It reads only the ClientHello --- the
first plaintext packet --- then either rejects the connection immediately (for clear
rule violations) or passes it through a scoring pipeline to make a disposition
decision. Connections that are allowed pass through byte-for-byte, with zero
modification to the TLS stream.

The pipeline has two stages: a \emph{fast path} that handles clear cases in
microseconds, and a \emph{signal collection} stage that runs eight parallel async
checks for everything else.

\subsection{The Fast Path}
\index{fast path!bypass rules}

Certain decisions do not require scoring. The fast path handles them without ever
consulting the signal collectors:

\begin{table}[ht]
  \small
  \begin{tabularx}{\linewidth}{L{3.8cm} L{2.4cm} L{2.4cm}}
    \toprule
    \textbf{Condition} & \textbf{Action} & \textbf{Why} \\
    \midrule
    \bypassrow{ALPN is \code{h2} or \code{h1}} & \badgeallow{} always & Browser; structural guarantee \\[3pt]
    \bypassrow{JA4 in whitelist} & \badgeallow{} always & Trusted client stack \\[3pt]
    \bypassrow{Valid mTLS client cert} & \badgeallow{} always & Cryptographic proof \\[3pt]
    \bypassrow{IP in static allowlist} & \badgeallow{} always & Operator-designated safe \\[3pt]
    \signalrow{JA4 in blacklist} & \badgeblock{} immediately & Known malicious TLS stack \\[3pt]
    \signalrow{Country in block list} & \badgeblock{} immediately & GeoIP enforcement \\[3pt]
    \signalrow{Spamhaus DROP/EDROP match} & \badgeblock{} immediately & Hijacked/unrouted space \\[3pt]
    \signalrow{TLS 1.0 or 1.1} & \badgeblock{} immediately & Obsolete protocol \\
    \bottomrule
  \end{tabularx}
  \caption{Fast-path decisions. Rows shaded blue are always-allow bypasses;
           grey rows are always-block bypasses. All are individually toggleable
           in \code{config/proxy.yml}.}
\end{table}

\sidenote{The ALPN browser bypass is an \emph{architectural} guarantee, not a
heuristic. Any TLS client that successfully negotiates HTTP/2 or HTTP/1.1 with your
backend is structurally indistinguishable from a real browser at the transport layer.
Blocking it would be a false positive by definition.}

\subsection{Signal Collection}
\index{signal collection}\index{async signals}

Connections that pass the fast path enter the signal collection stage. Eight checks
run in parallel --- all asynchronous, all fail-open if the underlying service is
unavailable:

\begin{enumerate}
  \item \textbf{TLS version and cipher enforcement} --- weak ciphers, export-grade
        suites, and anomalous extension patterns raise the risk score
  \item \textbf{SNI analysis} --- missing SNI, IP-literal hostnames, and
        algorithmically-generated domain names (DGA scoring) are flagged
  \item \textbf{TCP and connection behaviour} --- session resumption ratio, connection
        lifespan, concurrent connection count, and return-visitor history
  \item \textbf{ASN and datacenter classification} --- connections from datacenter
        ranges, Tor exit nodes, and known VPN providers receive elevated scores
  \item \textbf{FCrDNS enrichment} --- async PTR lookup; residential classification
        via forward-confirmed reverse DNS
  \item \textbf{Beaconing detection} --- inter-arrival time coefficient of variation
        over a sliding window; identifies automated periodic callers
  \item \textbf{AbuseIPDB reputation} --- scored reputation lookup with aggressive
        local caching; never hard-blocks on score alone below threshold 50
  \item \textbf{RDAP org reputation} --- organisation-level reputation from WHOIS/RDAP;
        configurable block expansion to \code{/24} (never beyond \code{/24} IPv4 or
        \code{/48} IPv6)
\end{enumerate}

\index{AbuseIPDB}\index{RDAP}\index{FCrDNS}\index{beaconing detection}
\index{ASN classification}\index{SNI analysis}

All eight signals are aggregated by the composite risk scorer into a single
integer score in the range 0--100. The action decider then consults the dial setting
to determine what action to take.

\subsection{The Dial}
\index{dial}\index{monitor mode}

The dial is a single integer, \configkey{dial} in \code{config/proxy.yml}, in the
range 0--100. It controls how aggressively \ja{} translates a risk score into a
blocking action.

At \textbf{\dialzero}, every connection is allowed regardless of score. The proxy
scores all traffic and records findings to Prometheus and the log stream, but takes
no blocking action. This is the default. On first deploy, nothing is blocked.

At \textbf{\dialhundred}, the configured score thresholds apply: connections scoring
above the block threshold are blocked, connections at intermediate scores may be
rate-limited or tarpitted.

\sidenote{You can raise the dial from 0 to 20 in production on day one, observe
the block list for a week, confirm no legitimate traffic appears, and then raise it
further. The dial increment limit in the config prevents accidental jumps to full
blocking.}

The separation between scoring and acting is intentional. Scores accumulate even at
dial=0, so by the time you decide to start blocking, you already have weeks of
historical data showing exactly what would have been blocked and why.

\begin{tipbox}[Recommended rollout]
  Deploy at \dialzero{}. Monitor for one to two weeks. Examine the Grafana dashboard
  to confirm that browser traffic (ALPN~=~\code{h2}/\code{h1}) never appears in
  the scored population. Confirm that high-score connections match known bad patterns.
  Then raise the dial to 20, observe for 48 hours, and continue incrementally.
\end{tipbox}

\section{What Gets Blocked}
\index{blocking}\index{C2 frameworks}\index{credential stuffing}
% ─────────────────────────────────────────────────────────────────────────────

\newthought{In testing against synthetic traffic corpora,} \ja{} blocks 94--99\% of
malicious traffic with zero false positives on real browser populations. That range
reflects the tunable dial: the lower bound is conservative (dial around 40); the
upper bound uses an aggressive threshold (dial 80--100) that may produce a small
number of false positives for automated API clients that are not pre-whitelisted.

\subsection{Known C2 Frameworks}
\index{C2 frameworks!Sliver}\index{C2 frameworks!Cobalt Strike}\index{C2 frameworks!Evilginx}

The JA4 blacklist ships with fingerprints for the default TLS stacks of Sliver,
Cobalt Strike, Evilginx, and several less widely-known implant frameworks. These are
hard-blocked on the fast path: when the JA4 fingerprint of the incoming ClientHello
matches a blacklist entry, the TCP connection is reset immediately, before any
payload is exchanged.

\sidenote{Attackers can modify their C2 framework's TLS configuration to change the
JA4 fingerprint. This is a real limitation. The response is layered defence: even if
the fingerprint is changed, the ASN, beaconing, and AbuseIPDB signals remain active.
A C2 operator who has changed their TLS config to evade JA4 typically still beacons
on a regular schedule and often operates from datacenter address space.}

\subsection{Spamhaus DROP and EDROP}
\index{Spamhaus DROP}\index{Spamhaus EDROP}

The Spamhaus Don't Route Or Peer (DROP) and Extended DROP (EDROP) lists enumerate
IP address ranges that have been hijacked, allocated for criminal use, or that belong
to networks with a history of systematic abuse. \ja{} loads and periodically refreshes
both lists into an in-process CIDR trie. Connections from listed ranges are hard-blocked
on the fast path with no further processing.

Both lists have very low false-positive rates: they are conservative by design, because
Spamhaus knows that legitimate ISPs sometimes operate in adjacent space.

\subsection{Rate-Based and Behavioural Detection}
\index{beaconing detection}\index{rate limiting}

The beaconing detector measures the coefficient of variation of inter-arrival times
for connections from a given IP address and JA4 fingerprint pair. Legitimate human
browsing is irregular. Automated tools --- whether scanners, credential stuffers, or
beaconing implants --- are periodic. A coefficient of variation below a configurable
threshold triggers a risk signal that contributes to the score.

The ASN classifier flags connections from cloud provider IP ranges (AWS, GCP, Azure,
DigitalOcean, and similar) because legitimate browser traffic does not originate from
datacenters. This is a \emph{signal}, not a hard block: many legitimate automated
API clients run from cloud infrastructure and should be pre-whitelisted.

\section{Deployment \& Integration}
\index{deployment}\index{Docker}\index{Kubernetes}\index{HAProxy}
% ─────────────────────────────────────────────────────────────────────────────

\newthought{The canonical \ja{} deployment sits between your existing load balancer
and your backend.} HAProxy (or any equivalent) handles TLS termination for your own
certificate --- or more precisely, it \emph{does not}: the key design point is that
HAProxy is configured in \emph{TCP proxy mode}, not TLS termination mode. It forwards
the raw TCP byte stream including the ClientHello to \ja{}, which reads the ClientHello
and then forwards the entire stream (unchanged) to the backend.

\index{TCP passthrough}

\begin{verbatim}
Internet  --TLS-->  HAProxy :443  --TCP-->  JA4proxy :8080  --TLS-->  Backend :443
                    (TCP mode)               (reads ClientHello,
                                             passes stream through)
\end{verbatim}

Your backend never changes. Your TLS certificate never moves. \ja{} is entirely
transparent to both the client and the backend.

\subsection{Docker Compose (POC and Staging)}
\index{Docker Compose}

For a proof of concept or staging deployment, the repository ships a
\code{docker-compose.yml} that brings up \ja{}, Redis, and the analytics node:

\begin{lstlisting}[language=bash, numbers=none]
git clone https://github.com/seanpor/JA4proxy
cd JA4proxy

# Start all services
make start

# Watch the live log stream
make logs

# Check proxy health
make health

# Stop everything
make stop
\end{lstlisting}

\sidenote{The default configuration starts at \dialzero{}. Nothing will be blocked
until you edit \code{config/proxy.yml} and set \configkey{dial} above zero, or use
the management API to update it at runtime.}

\subsection{Kubernetes (Production)}
\index{Kubernetes}\index{Helm}

A Helm chart is provided for Kubernetes deployments. \ja{} instances are stateless
(all shared state is in Redis), so horizontal scaling is straightforward:

\begin{lstlisting}[language=bash, numbers=none]
helm install ja4proxy ./helm/ja4proxy \
  --set replicaCount=4 \
  --set redis.host=redis.infra.svc.cluster.local \
  --set config.dial=0
\end{lstlisting}

\subsection{Horizontal Scaling}
\index{horizontal scaling}\index{Redis!cluster-wide bans}

Multiple \ja{} instances share a single Redis cluster. Bans are written to Redis
and therefore enforced cluster-wide: a connection blocked by instance~1 is also
blocked by instances 2, 3, and 4. Beaconing and return-visitor data is likewise
shared, so a client that distributes its requests across multiple instances is still
detected.

\section{Observability}
\index{observability}\index{Prometheus}\index{Grafana}\index{Loki}
% ─────────────────────────────────────────────────────────────────────────────

\newthought{\ja{} is designed to be observable from the first connection.} Every
action, every signal contribution, and every pipeline stage emits structured JSON
logs and Prometheus metrics. The repository ships a pre-built Grafana dashboard.

\subsection{Prometheus Metrics}
\index{Prometheus metrics}

All metrics follow the naming convention \code{ja4proxy\_\{subsystem\}\_\{metric\}\_\{unit\}}.
Key metrics include:

\begin{itemize}
  \item \code{ja4proxy\_connections\_total\{action\}} --- cumulative connection count
        broken down by final action (allow / block / tarpit / ban)
  \item \code{ja4proxy\_risk\_score\_distribution} --- histogram of risk scores
        across all scored connections
  \item \code{ja4proxy\_dial\_setting} --- current dial value as a gauge
  \item \code{ja4proxy\_signal\_latency\_seconds\{signal\}} --- latency of each
        signal collector, per-check
  \item \code{ja4proxy\_abuseipdb\_lookups\_total\{result\}} --- AbuseIPDB lookup
        cache hit/miss/error rate
  \item \code{ja4proxy\_spamhaus\_matches\_total} --- hard-block rate from DROP/EDROP
\end{itemize}

\sidenote{The Grafana dashboard ships with four panels: (1)~connection disposition
breakdown (allow/block/tarpit/ban over time), (2)~risk score histogram, (3)~top
JA4 fingerprints by connection count, and (4)~signal latency heatmap.}

\subsection{Log Format}
\index{log format!JSON}

All log lines are newline-delimited JSON. Every connection event includes:
\code{ts}, \code{level}, \code{event}, \code{src\_ip}, \code{ja4}, \code{score},
\code{action}, \code{reason}, \code{asn}, \code{asn\_org}, and \code{country}.
Logs are written to stdout for collection by your existing log aggregator
(Loki, Splunk, Elasticsearch, or any JSON-line-capable system).

\begin{notebox}[Log shipping]
  \ja{} does not buffer or batch logs internally. It writes one JSON line per event
  to stdout immediately. This means log volume is proportional to connection rate.
  At 350 conn/s you should expect roughly 30--50 MB/hour of uncompressed log data
  (most lines compress to 150--250 bytes).
\end{notebox}

\section{Safe Deployment: The Dial in Detail}
\index{dial!deployment strategy}
% ─────────────────────────────────────────────────────────────────────────────

\newthought{The single most important operational decision you will make} is how
quickly to raise the dial. Getting this wrong in one direction means your security
posture improves slowly; getting it wrong in the other direction means you block
legitimate traffic. \ja{}'s dial model is designed to make the second error very
unlikely.

The dial controls not just \emph{whether} to block, but also which actions to take
at which score thresholds. The default thresholds at dial=100 are:

\begin{table}[ht]
  \small
  \begin{tabularx}{\linewidth}{C{1.4cm} C{2.0cm} L{4.2cm}}
    \toprule
    \textbf{Score} & \textbf{Action} & \textbf{Typical cause} \\
    \midrule
    0--29   & \badgeallow  & Browser traffic, pre-whitelisted clients \\
    30--49  & \badgeallow  & Borderline automated; flagged in logs \\
    50--69  & \badgetarpit & Likely bot; connection accepted but stalled \\
    70--84  & \badgeblock  & High-confidence malicious; RST sent \\
    85--100 & \badgeban    & Confirmed malicious; 5-min ban in Redis \\
    \bottomrule
  \end{tabularx}
  \caption{Default score-to-action mapping at dial=100. At dial=0, all connections
           are allowed regardless of score. All thresholds are configurable.}
\end{table}

\index{tarpit}\index{ban!TTL}

\subsection{Tarpitting}
\index{tarpit}

The tarpit action accepts the TCP connection and then stalls it: responses are delayed
by progressively increasing intervals. From the attacker's perspective the service
appears to be slow. From your perspective the attacker's threads are occupied waiting
on a connection that will never deliver anything useful. This is more effective than
an immediate RST for slowing down distributed scanners, because the attacker cannot
simply retry faster.

\subsection{Self-Healing Bans}
\index{ban!self-healing}\index{TTL}

Every ban has a 5-minute TTL in Redis. After 5 minutes, the ban expires and the
IP address is treated as new again. This is a deliberate design decision rooted in
the asymmetry of errors: a false positive that bans a legitimate user self-heals
in 5 minutes. You are not required to manually review and clear bans to restore
service to legitimate users.

\sidenote{If you need longer bans for confirmed attacker infrastructure, you can
extend the TTL via the management API or by directly setting a longer TTL on the
Redis key. The 5-minute default is a safety net, not a ceiling.}

\subsection{Hot Config Reload}
\index{config!hot reload}\index{SIGHUP}

The dial and all threshold values can be changed without restarting \ja{}. Send
\code{SIGHUP} to the proxy process, or post a reload message via the management API.
The new config takes effect for all subsequent connections within milliseconds. This
means you can raise the dial conservatively, observe the effect in real time on the
Grafana dashboard, and immediately lower it again if you see unexpected blocks --- all
without any service interruption or connection gap.

\section{Project Status \& Roadmap}
\index{project status}\index{roadmap}
% ─────────────────────────────────────────────────────────────────────────────

\newthought{Honest status: \ja{} is a functional, tested proof of concept.}
The core pipeline works. The signal collectors work. The dial, the fast-path bypasses,
Spamhaus integration, and beaconing detection are all implemented and tested.
The codebase has comprehensive unit and integration tests, and a red-team adversarial
test suite.

What it is not, yet, is production-hardened for high-volume customer-facing
infrastructure. The gaps are documented in \code{docs/DMZ\_DEPLOYMENT\_READINESS.md}
in the repository.

\begin{importantbox}[Before production deployment --- read this]
  \code{docs/DMZ\_DEPLOYMENT\_READINESS.md} contains the full list of known gaps,
  their severity, and the roadmap for closing them. Do not deploy \ja{} in front of
  production traffic without reading and accepting that document.
\end{importantbox}

\subsection{The Go Rewrite (Phase 15)}
\index{Go rewrite}\index{throughput}

The current Python implementation achieves approximately 350 connections per second
on a single instance. For most deployments this is adequate. For high-volume
customer-facing infrastructure (hundreds of thousands of requests per minute), the
Go rewrite currently in progress targets a 10--50$\times$ throughput improvement.

The Go proxy achieves feature parity with the Python implementation including JA4
fingerprint computation, all fast-path bypasses, and the full signal collection
pipeline. The Python analytics node (which uses scipy and pandas for statistical
detection) remains Python: it is not on the hot path and its dependencies are not
practical to replicate in Go.

\subsection{Production Hardening Roadmap}
\index{roadmap!production hardening}

\sidenote{The Phase 200-series security posture is now live: Redis TLS

\section{For the Technical Evaluator}
\index{technical evaluation}\index{design philosophy}
% ─────────────────────────────────────────────────────────────────────────────

\newthought{If you are the senior engineer deciding whether this is technically sound,}
this section is written for you. The design philosophy, the architectural decisions,
and the known limitations are described plainly.

\subsection{The Core Asymmetry}
\index{false positive}\index{false negative}\index{fail open}

The entire system is designed around a fundamental asymmetry: a false negative (a bad
bot slips through) is recoverable. A false positive (a real browser is blocked) is not.
This asymmetry drives every caching TTL, every threshold default, and every fallback
behaviour in the codebase:

\begin{itemize}
  \item ALLOW decisions are cached with long TTLs. BLOCK decisions with short TTLs.
  \item When Redis says block but the local in-process cache says allow: \emph{local
        cache wins.} If Redis goes down, real users keep working.
  \item When any external service (AbuseIPDB, RDAP, DNS) is unreachable, the signal
        that service would have contributed is zeroed. The connection scores lower, not
        higher. Fail open, always.
  \item The ALPN browser bypass cannot be defeated by a misconfigured dial. Even if
        you set the dial to 100 and the thresholds to 0, browser traffic bypasses the
        scorer entirely.
  \item Default dial is 0. You must consciously raise it.
\end{itemize}

\subsection{Signal Collection Design}
\index{async signals!design}

All eight signal collectors run concurrently via \code{asyncio.gather()}. No signal
waits on another. The composite scorer receives all eight results and computes a
weighted sum. Each signal has a configurable weight and a configurable cap (the maximum
contribution a single signal can make to the total score), preventing any single
data source from dominating the decision.

External service calls (AbuseIPDB, RDAP, DNS) are fire-and-forget from the hot path:
they are initiated by \code{asyncio.create\_task()} and the result is stored in Redis
for use on the \emph{next} connection from that IP. This means the first connection
from a new IP may score lower than it would on subsequent connections, because the
enrichment data has not yet arrived. This is intentional: it is better to miss one
connection from a new bad actor than to add latency to every first connection.

\sidenote{The enrichment pipeline is designed for returning callers. A credential
stuffer making a single request from each of 10\,000 IPs will not trigger beaconing
detection and will receive limited enrichment. This is a known gap; the AbuseIPDB
signal provides partial coverage for this pattern.}

\subsection{No Blocking I/O on the Hot Path}
\index{hot path!non-blocking}

There is no blocking I/O on the connection-handling hot path. All Redis reads are
pipelined. The Spamhaus trie and ASN database are loaded into process memory at
startup and queried in-process (no network round-trip). GeoIP lookups use the
MaxMind mmap interface. The JA4 fingerprint computation is pure CPU, typically
completing in under 50 microseconds.

\subsection{IPv6 Support}
\index{IPv6}

IPv6 is handled throughout the pipeline. IP-keyed Redis structures (bans, rate
limiting, beaconing timestamps, return-visitor history) use the full IPv6 address
string as the key. CIDR matching uses \code{pytricia}, which handles both address
families natively. Subnet-level analytics use \code{/48} prefixes for IPv6 (the
approximate equivalent of IPv4 \code{/24} in terms of user population density).
Block expansion via RDAP is capped at \code{/48} for IPv6.

\subsection{Performance Test Methodology}
\index{performance testing}

Throughput figures in this document are from single-box testing using synthetic TLS
ClientHello packets replayed at controlled rates against a local JA4proxy instance
with a real Redis backend. The test corpus includes browser fingerprints (Chrome,
Firefox, Safari, Edge), scanner fingerprints (nmap, masscan, zgrab2), and C2
framework fingerprints. Tests were run on commodity hardware (8-core, 16 GB RAM,
local Redis on the same host).

\begin{notebox}[Test environment caveat]
  The 350 conn/s Python baseline was measured with all eight signal collectors active
  and Redis on localhost. In a deployment where Redis is on a separate host with
  1--5\,ms round-trip latency, throughput will be lower. The Go rewrite uses Redis
  pipelining aggressively and is less sensitive to Redis round-trip latency.
\end{notebox}

\subsection{What the Codebase Looks Like}

\ja{} is approximately 4\,000 lines of Python (proxy and signal collectors) plus
3\,500 lines of Go (rewrite in progress). The Python codebase has approximately
5\,200 lines of tests. The test suite includes unit tests, integration tests against
a live Redis instance, chaos tests (simulating Redis failures, network partitions, and
external service unavailability), and an adversarial test suite that replays known
malicious TLS fingerprints.

Type hints are used throughout the Python codebase. All public functions and classes
have docstrings. The Go codebase is \code{gofmt}-formatted with godoc comments on all
exported symbols. There are no known open security issues in the vulnerability tracker.

\sidenote{The test-to-code ratio is maintained at approximately 1.3$\times$ throughout
the project. New signals must include unit tests, an integration test, and at least one
chaos test verifying the fail-open behaviour before they can be merged.}

\subsection{Limitations You Should Know}

\begin{warningbox}[Known limitations]
  \begin{itemize}
    \item \textbf{First-connection enrichment gap:} AbuseIPDB and RDAP scores arrive
          asynchronously. The first connection from a new IP may score lower than
          warranted.
    \item \textbf{JA4 fingerprint modification:} A sophisticated attacker can change
          their C2 framework's TLS configuration. Layered signals (ASN, beaconing,
          AbuseIPDB) provide coverage when this happens, but a sufficiently careful
          attacker can reduce their score.
    \item \textbf{Python throughput ceiling:} At 350 conn/s per instance, very
          high-volume deployments require many instances. The Go rewrite addresses this.
    \item \textbf{Shared IP addresses:} AbuseIPDB scores for shared IPs (NAT gateways,
          large VPNs) can be high without indicating malicious intent from the current
          user. Hard-blocking is deliberately avoided below AbuseIPDB score 50.
    \item \textbf{Not yet production-hardened:} See \code{docs/DMZ\_DEPLOYMENT\_READINESS.md}.
  \end{itemize}
\end{warningbox}
