\chapter{Installation}
\label{ch:installation}
\index{installation}\newthought{JA4proxy can be deployed either as a systemd service} (supporting containerized Docker Compose or native Go binaries) or run manually via Docker Compose for local development. For production environments, we provide a secure, zero-compile bootstrapper that installs dependencies, runs the native Go configuration wizard (\code{ja4p init}), sets up system-level integrations (systemd, logrotate, daily cron backups), and configures host firewall rules.

This chapter covers both the production automated deployment and the local development setup.

\begin{warningbox}[Zero-Compile Production Posture]
To minimize attack surface, production hosts must not carry compilers or build tools (such as \code{gcc}, \code{make}, or \code{go}). The bootstrapper enforces this rule at startup when running in production. Pre-built binaries or container images must be used.
\end{warningbox}

\subsection{Ports}

The following ports are used on the host. In production, only the public ingress port (\code{443}) should be exposed to the public internet. All management and metrics ports should be restricted to loopback (\code{127.0.0.1}) and accessed via VPN or SSH tunnels.

\begin{table}[ht]
  \small
  \begin{tabularx}{\linewidth}{llX}
    \toprule
    \textbf{Port} & \textbf{Service} & \textbf{Purpose} \\
    \midrule
    443 & HAProxy / Ingress & Public TLS entry point (inbound traffic) \\
    8443 & JA4proxy & Proxy TLS entry point (receives traffic from HAProxy or iptables redirect) \\
    8090 & Management UI & FastAPI dashboard (plain HTTP, loopback only — access via SSH tunnel) \\
    8444 & Management UI HTTPS & Caddy TLS sidecar for management dashboard (self-signed cert) \\
    9090 & JA4proxy metrics & Prometheus scrape endpoint (proxy) \\
    9091 & Prometheus & Prometheus query UI \\
    3000 & Grafana & Visual analytics dashboards \\
    \bottomrule
  \end{tabularx}
  \caption{Port assignments}
\end{table}

\subsection{System Resources}

The full stack requires:
\begin{itemize}
  \item 4 GB RAM available
  \item 2 CPU cores
  \item 5 GB disk (images + GeoIP databases + logs)
\end{itemize}

\section{Production Deployment (Automated)}
\index{production deployment}
\index{bootstrap.sh}
\index{ja4p init@\code{ja4p init}}

The production installer automates system dependencies, user creation, config generation, log rotation, cron backups, and firewall rules.

\subsection{Step 1: Run the Bootstrapper}
On a clean host machine, run the bootstrapper script as root:
\begin{bashcode}
sudo ./scripts/bootstrap.sh
\end{bashcode}
By default, this runs in containerized mode. To use native systemd binaries instead, run:
\begin{bashcode}
sudo ./scripts/bootstrap.sh --mode native
\end{bashcode}

\subsection{Step 2: Setup Wizard}
The bootstrapper automatically launches the native Go configuration wizard (\code{ja4p init}). It will walk you through:
\begin{enumerate}
  \item \textbf{Backend Host/Port:} The address and port of your protected backend web server.
  \item \textbf{Deployment Mode:} Run as native binaries or Docker containers.
  \item \textbf{Bind IP:} The local IP for management services (default \code{127.0.0.1} for security).
  \item \textbf{Credentials:} Admin username and password for the Management UI.
  \item \textbf{Networking:} Upstream load balancer, PROXY protocol, allowed SNIs.
  \item \textbf{TLS Certificates:} Self-signed or user-supplied certificates.
  \item \textbf{Threat Intel Keys:} Optional API keys for AbuseIPDB, GreyNoise, MISP, and others.
  \item \textbf{Hardening:} Firewall backend, Fail2Ban, CrowdSec, monitoring stack, backup encryption.
\end{enumerate}

\begin{warningbox}[Secrets are Never Echoed]
To comply with security guidelines, the wizard never prints generated secrets (e.g. Redis passwords, JWT signing keys) to the screen. They are written directly to \code{.env} with secure permissions (\code{chmod 0600}).
\end{warningbox}

\subsection{Step 3: Generated Files}
The wizard generates four configuration files:
\begin{itemize}
  \item \code{.env} --- Secret environment variables (chmod 600), including generated passwords and keys.
  \item \code{config/proxy.yml} --- JA4proxy daemon configuration (backend, signals, scoring, logging).
  \item \code{config/haproxy.cfg} --- HAProxy configuration for multi-proxy deployments (container mode only).
  \item \code{/etc/systemd/system/ja4proxy.service} --- systemd unit for production service management.
\end{itemize}

\subsection{Step 4: Service Integration}
Once complete, the bootstrapper integrates the service into the host operating system:
\begin{itemize}
  \item \textbf{systemd Unit:} Creates and starts \code{ja4proxy.service}.
  \item \textbf{Firewall (UFW/FirewallD):} Exposes ports \code{80}/\code{443} publicly; restricts admin ports (\code{8090}, \code{9090}, \code{9091}, \code{3000}) to the local loopback.
  \item \textbf{Logrotate:} Configures log rotation under \code{/var/log/ja4proxy} (caps logs at 10M, keeping 3 rotations).
  \item \textbf{Backups:} Installs a daily cron job at 03:30 to package configuration and database files under \code{/backup/ja4proxy} with 14-day retention.
\end{itemize}

\begin{notebox}[Air-Gapped Environments]
If your production host is air-gapped, copy the pre-built \code{ja4proxy-offline.tar.gz} bundle next to the repository. The bootstrapper will automatically load it via \code{docker load} without requiring external network access.
\end{notebox}

\section{Local Development Deployment (Manual)}
\index{development setup}
\index{make start}

For local development or testing, you can run the Docker Compose stack manually.

\subsection{Step 1: Clone the Repository}
\begin{bashcode}
git clone https://github.com/seanpor/JA4proxy.git
cd JA4proxy
\end{bashcode}

\subsection{Step 2: Create the Environment File}
\begin{bashcode}
cp .env.example .env
\end{bashcode}
Edit the file to configure your \code{BACKEND\_HOST} and credentials.

\subsection{Step 3: Start the stack}

\begin{bashcode}
docker compose pull && docker compose up -d
\end{bashcode}

\begin{tipbox}[Pre-built images — no build step needed]
Both the Go proxy and the management API are published as container images to the
GitHub Container Registry (GHCR) on every merge to \code{main}. Running
\code{docker compose pull} fetches them automatically. No compiler or build tools
are required on the host:
\begin{lstlisting}[language=bash, numbers=none]
ghcr.io/seanpor/ja4proxy-go:main
ghcr.io/seanpor/ja4proxy-management:main
\end{lstlisting}
Both packages are public. \code{docker compose build} is only needed when
developing changes to the proxy or management API locally.
\end{tipbox}

\subsection{Step 4: Download GeoIP Data}
To enable country classification in development:
\begin{bashcode}
make update-geoip
\end{bashcode}

\section{Verifying the Installation}
\index{verification}
\index{health check}

\subsection{Service Status}
Verify that the systemd service is active:
\begin{bashcode}
systemctl status ja4proxy.service
\end{bashcode}
Or check the container statuses:
\begin{bashcode}
docker compose ps
\end{bashcode}

\subsection{Proxy Health Endpoint}
Verify the local health API returns a healthy status:
\begin{bashcode}
curl -s http://127.0.0.1:8090/api/v1/health
# Expected: {"status":"ok",...}
\end{bashcode}

\subsection{Grafana Dashboard}
Access Grafana at \url{http://127.0.0.1:3000}. Check that the \emph{JA4proxy Overview} dashboard is present. To generate test traffic to verify dashboards:
\begin{bashcode}
./scripts/generate-tls-traffic.sh 30 50 5
\end{bashcode}

\section{Building the Proxy from Source}
\index{Go proxy}
\index{ja4pd}

The production proxy is implemented in Go (\code{cmd/ja4pd}). To build the binaries locally:
\begin{bashcode}
make build            # builds bin/ja4pd and bin/ja4p
\end{bashcode}

\section{Stopping \& Uninstalling the Stack}
\index{stopping the service}

To stop the systemd service in production:
\begin{bashcode}
sudo systemctl stop ja4proxy.service
\end{bashcode}

To completely uninstall JA4proxy and clean all directories:
\begin{bashcode}
sudo ./scripts/bootstrap.sh --uninstall
\end{bashcode}

For development setups:
\begin{bashcode}
make stop             # stops containers, keeping data
make stop-clean       # stops containers and purges volumes
\end{bashcode}
