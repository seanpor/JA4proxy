## The test range (leave it up; rebuilds fast)

Documented in `docs/security/pentest/RANGE.md`. It is `docker-compose.poc.yml`
+ a `docker-compose.pentest.yml` override — i.e. **the stack that actually
ships**, with every network forced internal (zero egress, asserted on every
bring-up) and an `attacker` container to work from.

```bash
make pentest-range          # build, start, and VERIFY isolation + provenance
make pentest-shell          # shell on the attacker workstation (attack from here)
make pentest-range-verify   # re-run the 8 isolation assertions, no rebuild
make pentest-range-down     # tear down (evidence kept)
```

It is **currently up** (8 containers). `make pentest-range` is idempotent and
rebuilds in a few minutes if torn down. It runs in **production posture** by
default (attacking a dev-posture build gives false results). Evidence goes to
`.pentest-range/evidence/` (gitignored, 12-month retention).

## Hard-won process lessons (these cost the session — don't repeat them)

1. **Run the full gates locally before pushing**: `make scan`, `make lint`,
   `make test`. Not the fast subset. A PR pushed on the fast subset is how CI
   surprises you.
2. **Read the gate's LOG, not its exit code.** `make scan` wrapped in a shell
   `; echo` reports the echo's exit (0), not the scan's. Grep the log for
   `make .* Error`, `✗`, `HIGH/CRITICAL in`. This caught every wrong turn.
3. **`make test` failures are truncated inside Docker** (see PHASE_816) — if
   `make test` fails with no detail, re-run the failing dir with
   `docker run ... -e PYTEST_XDIST_WORKER=debug ja4proxy-tools pytest <dir> -q`.
4. **Container-strict** (`AGENTS.md`): never run pytest/ruff/pip on the host —
   use `make` targets (they run in the pinned `ja4proxy-tools` image). Go tests
   run natively.
5. **`main` is branch-protected**: PRs only, 4 required checks (Meta-Validation,
   Full Lint, Full Test, Security Scan). `gh pr create` → `gh pr merge --auto
   --squash --delete-branch`.
6. **Some `.trivyignore` CVEs are unfixable by us** — `GHSA-6v7p-g79w-8964`
   (msgpack) and `CVE-2025-47273` (setuptools) are *pip's own vendored copies*
   (`pip/_vendor`). Bumping the Python base does NOT clear them. Don't waste
   time "fixing" them; they're correctly exceptioned.
7. **Phase close-out** (`AGENTS.md` Rule 4): mark COMPLETE in `manifest.yaml`,
   **move the phase doc to `docs/phases/complete/`**, add a `CHANGELOG.md` entry
   (the manifest gate reads `CHANGELOG.md` directly — a fragment alone won't
   pass), all in one commit.
